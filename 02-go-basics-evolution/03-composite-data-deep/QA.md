# 专题 03：切片与 Map 底层大厂高频面试题

---

### Q1: 切片（Slice）和数组（Array）的核心区别是什么？传递给函数会有什么不同？

**标准回答**：
- **类型定义**：数组是值类型，长度是类型系统的一部分（`[3]int` 与 `[4]int` 是不同类型）；切片是引用语义的动态容器，类型声明为 `[]int`。
- **内存模型**：切片自身是一个 24 字节的小结构体（`SliceHeader`：包含 1 个底层数组指针 `Data`、`Len` 和 `Cap`）。
- **函数传递差异**：
  - 数组传参时，会触发**整个连续数组的深拷贝**（若数组极大，开销惊人）。
  - 切片传参时，发生的是 **SliceHeader 的值传递**（仅拷贝 24 字节）。函数内部对切片元素的直接修改（如 `s[0] = 10`）会影响外层，因为二者共享同一个底层数组；但如果在函数内发生 `append` 触发了扩容分配了新数组，外层切片的 `Data` 指针并不会改变，外层将感知不到新 append 的数据。

### Q2: 为什么 Go 1.18+ 要对切片扩容机制进行重构？新版扩容规则是怎样的？

**标准回答**：
- **旧版痛点（1.17 及更早）**：以前以 1024 为界限（<1024 翻倍，>=1024 扩容 1.25x），在 1024 临界点前后扩容速率发生**断崖式骤降**（从 2.0x 陡降至 1.25x），且内存分配利用率不高。
- **Go 1.18+ 新机制**：
  1. 阈值下调为 **256**。
  2. 当 `oldcap < 256` 时，依然维持 **2.0 倍翻倍**增长。
  3. 当 `oldcap >= 256` 时，使用平滑过渡公式：$\text{newcap} = \text{oldcap} + \frac{\text{oldcap} + 3 \times 256}{4}$。这使得扩容系数从 2.0x 极其平滑地逐渐衰减至 1.25x，彻底消除了断崖突变。
  4. 最终结合运行时的内存块规格（`roundupsize`）向上对齐，得到实际匹配的物理空间。

### Q3: 为什么 Map 并发写会直接抛出 fatal error 而不是 panic？能够用 recover 捕获吗？

**标准回答**：
- **无法捕获**：`fatal error` 是 Go 运行时检测到严重的内存或状态损坏时的硬崩溃信号，**完全无法被用户的 `recover()` 捕获**，会直接将调用栈打印至 stderr 并强制终止整个进程。
- **设计原因**：Go 官方认为，Map 并发读写表明程序的共享内存状态已经处于极度危险的不可预测竞态破坏之中（底层哈希链表、桶迁移指针可能已经被写乱）。如果允许 recover 吞掉异常继续运行，后续可能会导致严重的数据腐化、静默写入错误或内存非法访问。为了避免更加隐蔽的业务灾难，Go 选择了最果断的“快速失败（Fail-Fast）”机制。

### Q4: 什么是三索引切片 `s[i:j:k]`？在大厂开发中有什么用？

**标准回答**：
- **定义**：全切片表达式（Full Slice Expression），语法为 `slice[low:high:max]`。
  - `len = high - low`
  - `cap = max - low`
- **核心价值（内存安全隔离）**：
  - 默认的双索引切片 `s[i:j]` 其 `cap` 会一直延伸到底层数组的末尾。若对子切片执行 `append`，只要底层数组剩余空间够用，子切片就会直接覆盖写入底层数组后续的位置，**无形中污染了原切片未修改的数据**！
  - 通过三索引切片 `s[low:high:high]`，将子切片的 `cap` 强制锁定等于 `len`。后续子切片一旦发生任何 `append`，都会强迫运行时为子切片开辟**全新的独立内存空间**，从而彻底隔绝子切片与原切片，避免深坑级的数据污染 Bug。
