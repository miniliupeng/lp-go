# 专题 02：内存模型、逃逸分析与 GC 大厂高频面试题

---

### Q1: 指向局部变量的指针，在 Go 中一定会逃逸到堆上吗？

**标准回答**：
**不一定**。
虽然“函数返回局部变量指针”会 100% 导致逃逸，但如果函数被编译器判定为**可以安全内联（Inlining）**，且内联后该指针的生命周期依然没有超出外层调用者的栈帧生命周期，编译器就会运用内联优化，**直接将该对象分配在外层函数的栈上，从而避免堆逃逸**。可以通过 `go build -gcflags="-m -m"` 观察内联决策。

### Q2: 为什么 Go 语言在微小对象分配时设计了 Tiny 分配器？

**标准回答**：
- **痛点**：高并发系统中存在海量的小于 16 字节的对象（如 `*int`、小型闭包、包含单个小字段的结构体）。若每个对象都单独分配一个 8KB 或更大的内存页，会产生极其严重的**内存碎片率**，而且频繁进入分配流程会浪费大量 CPU。
- **机制**：Go 的 `mcache` 为每个逻辑处理器 P 配备了 Tiny 分配器（一个 16 字节的微分配块）。它将多个小于 16B 且不含指针的小对象**合并打包存放在同一个 16B 块中**，仅当这一块用尽时才申请下一个 Tiny 块，从而将微小对象的分配开销和内存浪费降到最低。

### Q3: 为什么 Dijkstra 插入写屏障最后必须进行 STW 重新扫描栈？

**标准回答**：
- **性能权衡**：栈是协程极高频读写的核心区域。如果在栈上每一次指针写入都执行写屏障（触发函数调用与标灰逻辑），会使整个程序的运行性能下降 20%~40%。因此 Go 1.5 在实现插入写屏障时，**选择仅在【堆】上开启屏障，在【栈】上不开启**。
- **漏标风险**：在标记阶段并发运行中，栈上的黑色对象可能会直接引用堆上的某个白色对象，而此时因为栈上没有写屏障，该白色对象无法被自动标灰。
- **代价**：为了避免该白色对象被错误回收，Dijkstra 插入屏障在标记即将完成时，**必须强制进行第二次 STW（Stop The World），暂停所有协程，重新完整扫描一次所有活跃协程的栈空间**，这一步重新扫描会产生数十毫秒甚至更长的 STW 停顿。

### Q4: Go 1.8 混合写屏障（Hybrid Write Barrier）是如何做到消除二次 STW 的？

**标准回答**：
混合写屏障结合了插入写屏障与删除写屏障的优势，并制定了四条铁律：
1. **栈上新建对象直接标黑**：GC 标记期间，协程栈上新建的任何对象，直接标记为【黑色】（不需要被重复扫描）。
2. **栈上指针修改不加屏障**：栈操作依然保持原生极速，不插桩写屏障。
3. **堆上修改指针，旧对象强制标灰**：堆上的指针被覆盖或删除时，将其原本引用的旧对象标记为【灰色】（Yuasa 删除屏障特性，保护下游白色对象）。
4. **堆上新增引用，新对象强制标灰**：堆上新增指针引用时，将其指向的目标新对象也标记为【灰色】（Dijkstra 插入屏障特性）。
- **结论**：由于栈上新对象始终为黑，且任何从栈逃逸或在堆上流转的指针都会在堆屏障处被标灰，使得栈上的任何黑色对象永远不可能直接引用到未受保护的白色对象，**从而彻底消除了最后重新扫描栈的 STW 过程**，将 STW 控制在 1 毫秒以内。

### Q5: 为什么 Go 没有采用 Java HotSpot 那样的分代垃圾回收（Generational GC）？

**标准回答**：
Java 依赖分代假说（“绝大多数对象朝生夕死”），在新生代高频 Minor GC，是因为 Java 中几乎所有对象（甚至哪怕只是一个小型 POJO）都强制分配在堆上。
而 Go 之所以不需要分代 GC，是因为：
1. **逃逸分析的天然筛选**：Go 在编译期通过严密的逃逸分析，已经把 80% 以上“朝生夕死”的临时对象全部直接分配在**栈**上，随函数返回直接出栈销毁，压根不会流进堆给 GC 带来负担。
2. **写屏障开销权衡**：分代 GC 必须维护记忆集（Remembered Set）和卡表（Card Table）来追踪老年代对新生代的跨代引用，这会导致每次指针写操作都有额外的写屏障开销。Go 追求极致的高并发与超低吞吐损耗，采用逃逸分析配合单代并发标记更轻量高效。

### Q6: 在 Kubernetes 容器中部署 Go 服务，为什么单纯调 `GOGC` 容易 OOM，如何配合 `GOMEMLIMIT` 调优？

**标准回答**：
- **原因**：传统的 `GOGC` 是相对比例触发器（如默认 `GOGC=100` 表示当前存活堆内存翻倍时触发下次 GC）。在容器分配了 1GB 内存的情况下，如果存活对象达到 600MB，GC 将在 1200MB 才触发，但此时容器已经在 1024MB 被 Linux cgroup 的 OOM Killer 强杀。若盲目把 GOGC 调低（如 20），在流量平稳时又会引发过度的无意义 GC 导致 CPU 飙高。
- **最佳实践**：
  1. 将 **`GOMEMLIMIT` 设置为容器内存硬限制的 80% ~ 90%**（例如容器 Limit 为 1GiB，设置 `GOMEMLIMIT=850MiB`，留 150MB 给操作系统 pagecache 和非 Go 运行时内存）。
  2. **适当调大 `GOGC`**（如保持 100 甚至提高到 150）：在低内存水位时减少 GC 频次节约 CPU，而一旦业务流量突增导致内存逼近 850MB 时，`GOMEMLIMIT` 机制会强制介入接管，自适应触发高频 GC 压制内存，做到“平时省 CPU，高峰防 OOM”的双重保障。
