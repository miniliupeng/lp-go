# 专题 03：Channel 底层、Mutex 状态机与 sync.Pool 大厂高频面试题

---

### Q1: 向一个已经关闭（Closed）的 Channel 发送数据和接收数据，分别会发生什么？为什么？

**标准回答**：
- **发送数据**：直接触发 **`panic: send on closed channel`**。
  - 底层机理：在 `chansend()` 源码中，获取锁后首先检查 `if c.closed != 0`，若已关闭则直接调用 `panic` 抛出不可恢复异常。
- **接收数据**：
  1. 如果**缓冲区内仍有剩余数据**，则继续正常读取旧数据，返回 `v, true`；
  2. 当**缓冲区数据全部读空**后，再次读取会**立即返回该类型的零值和 `false`**（不会阻塞）。
  - 底层机理：`chanrecv()` 检查到 `c.closed != 0 && c.qcount == 0` 时，解锁并直接将目标地址清零，返回 `selected = true, received = false`。

### Q2: 为什么 Goroutine 被 Channel 阻塞时使用的是 `sudog` 而不是直接把 `g` 结构体挂在队列上？

**标准回答**：
- **多对多解耦关系**：一个 Goroutine（`g`）同一时刻可能参与多个等待队列！最典型的场景就是 **`select` 语句**：
  - 一个 Goroutine 可以同时在 5 个不同 Channel 上监听等待读写事件；
  - 如果直接将 `g` 挂在 Channel 的等待队列上，一个 `g` 无法同时处于 5 个不同的双向链表中（链表指针 `next`/`prev` 冲突）；
- **`sudog` 充当伪代理节点**：`sudog` 是 `g` 在特定 Channel 等待事件上的独立包装载体。一个 `g` 可以拥有多个 `sudog` 分别挂在不同 Channel 的 `recvq`/`sendq` 中，只要其中任意一个 Channel 就绪，调度器就能通过 `sudog.elem` 完成数据交接并唤醒 `g`，同时将其余相关的 `sudog` 从其他队列中解绑清理。

### Q3: `sync.Mutex` 的自旋（Spinning）条件是什么？为什么不一直自旋？

**标准回答**：
- **自旋准入条件**（四项铁律）：
  1. 锁处于**正常模式**（饥饿模式下绝对禁止自旋）；
  2. 运行机器是**多核 CPU**（单核自旋无法等待持有者释放，纯属浪费）；
  3. 当前进程的逻辑处理器数 `GOMAXPROCS > 1`；
  4. 当前 P 的本地运行队列为空（避免自旋阻碍其他可运行 G 的调度）；
  5. 累计自旋次数不超过 **4 次**（通过 CPU 的 `PAUSE` 指令空转）。
- **限制自旋的原因**：自旋虽然能避免协程挂起和操作系统上下文切换，但它以 100% 消耗 CPU 计算资源为代价。若 4 次自旋后仍未拿到锁，说明临界区耗时较长，继续自旋性价比极低，必须转入 `runtime.gopark` 休眠排队。

### Q4: `sync.Mutex` 是可重入锁（Reentrant Lock）吗？为什么官方坚持不提供可重入特性？

**标准回答**：
- **结论**：**不是可重入锁**。同一个 Goroutine 在未释放的情况下再次对同一个 Mutex 调用 `Lock()`，会导致**永久死锁**。
- **设计哲学**：
  1. Go 语言设计者（Rob Pike、Russ Cox）认为**可重入锁是糟糕设计的温床**。需要可重入锁通常意味着函数的临界区边界模糊、并发锁颗粒度控制混乱。
  2. 性能极致追求：可重入锁必须在每次 `Lock/Unlock` 时额外记录当前持有锁的 Goroutine ID（`goid`）与递归调用计数器，这会引入显著的额外性能损耗与竞态判断。
  3. Go 推荐的模式是将公共业务逻辑提取为内部非导出函数（无锁版本），由外层导出的公开函数负责加解锁。

### Q5: `sync.Pool` 为什么不能当作数据库连接池（Connection Pool）或线程池使用？

**标准回答**：
- **原因 1：对象生命周期不受控**。`sync.Pool` 中的对象会在发生 2 轮垃圾回收后被**静默回收清理**，没有任何保活机制与回收通知回调。如果将长连接（如 MySQL TCP 连接）放入其中，连接对象被 GC 回收后，底层的操作系统网络套接字（Socket）可能会发生泄漏或突然断开。
- **原因 2：无最大容量与排队阻塞控制**。`sync.Pool` 是纯粹的**临时内存对象缓存池**，当池为空时它会直接调用 `New` 创建新对象，无法限制最大活跃并发数，因此无法起到数据库连接池的“限流防压垮”保护作用。
- **正确定位**：专门用于高频短周期的纯内存对象复用（如 `bytes.Buffer`、协议编解码临时结构体），用以消除 GC 堆分配。

---

- **写优先机制**：当某个协程申请写锁 `Lock()` 时，`RWMutex` 会通过将读计数器原子减去一个极大的常量（`rwmutexMaxReaders = 1 << 30`），使得所有后续到来的新读锁 `RLock()` 立即被强行阻塞排队。当已持有读锁的协程全部释放完毕后，该写锁优先执行，从而杜绝写饥饿。

### Q7: `sync.Once` 为什么不能单纯只靠 `atomic.CompareAndSwap` 实现？

**标准回答**：
- **致命缺陷（未完全初始化返回）**：如果只用 CAS：
  ```go
  if atomic.CompareAndSwapUint32(&done, 0, 1) {
      f()
  }
  ```
  当协程 A 成功将 `done` 从 0 置为 1 时，开始执行 `f()`（假设 `f` 初始化耗时 20ms）。
  此时并发的协程 B 进入，调用 CAS 发现已经是 1，直接判定初始化成功并返回！**但此时协程 A 根本还没初始化完成**，协程 B 拿着未初始化完毕的空指针去访问，直接导致 **`panic: nil pointer dereference`** 空指针崩溃！
- **正确解法**：`sync.Once` 必须采用**双重检查锁（DCL）**：未完成时进入慢路径加互斥锁，协程 B 必须阻塞在锁上等待协程 A 的 `f()` **真正执行完毕解锁并发布 `done=1`**，确保返回给外部调用方时对象已经绝对就绪。

### Q8: `sync.Map` 的读写分离底层原理是什么？为什么在“高频写入”场景下性能反而远不如普通 `RWMutex + map`？

**标准回答**：
- **适用场景**：
  1. 读极多、写极少（如配置中心数据、路由元信息缓存）；
  2. 多个协程并发读写不相交的 Key。
- **高频写性能极差的根因**：
  1. **写操作始终加互斥锁**：任何新 Key 的写入都必须先获取 `m.mu` 互斥锁，并写入 `dirty` 字典；
  2. **脏字典提升时的全量内存浅拷贝**：当在 `read` 中查找未命中达到 `misses >= len(dirty)` 时，会触发将 `dirty` 提升为 `read`；而在下一次有新 Key 写入时，又必须**加锁遍历旧 `read`，把未被删除的条目逐一复制一份到新的 `dirty` 字典**中！
  3. **结论**：若在高频增删 Key 的场景下使用 `sync.Map`，会频繁触发全量浅拷贝与互斥锁争用，开销极大。高频写场景应当使用**分段锁（Sharded Map / ConcurrentMap）**或普通带锁 Map。
