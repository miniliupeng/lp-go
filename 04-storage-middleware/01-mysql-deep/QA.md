# 专题 01：MySQL InnoDB 存储引擎、锁与事务大厂高频面试题

---

### Q1: 既然可重复读（RR）隔离级别能解决不可重复读和快照读下的幻读，为什么在 RR 下依然可能出现“当前读幻读”？

**标准回答**：
- **快照读（Snapshot Read）**：普通 `SELECT` 依托 MVCC ReadView，在整个事务期间读取的是同一份历史快照，因此**不会看到其他事务新插入的数据，此时无幻读**。
- **当前读（Current Read）**：`SELECT FOR UPDATE`、`UPDATE`、`DELETE` 会强制读取记录的最新版本，并加锁。
- **出现幻读的经典场景**：
  1. 事务 A 开启，执行快照读 `SELECT * FROM users WHERE id = 5`，返回空；
  2. 事务 B 插入了 `id = 5` 并成功 `COMMIT`；
  3. 事务 A 执行当前读操作 `UPDATE users SET name = 'neo' WHERE id = 5;`。由于是当前读，事务 A 成功找到了事务 B 刚插入的这条数据并更新成功，导致该记录的最新版本上的 `trx_id` 变成了事务 A 自己的 ID！
  4. 事务 A 再次执行快照读 `SELECT * FROM users WHERE id = 5`。根据 MVCC 第一条规则（`trx_id == creator_trx_id` 自身修改可见），原本查不到的数据突然凭空出现了！
- **规避方案**：如果业务需要防止幻读，必须在事务一开始就使用当前读 `SELECT ... FOR UPDATE`，通过加 Next-Key Lock 锁死间隙，彻底禁止其他事务并发插入。

### Q2: 为什么 InnoDB 的 B+ 树层高通常只有 3 到 4 层？它是如何计算出来的？

**标准回答**：
- **核心计算推演**：
  - InnoDB 的基本存储单元是 **数据页（Page）**，默认大小为 **16KB**；
  - 假设主键使用 `BIGINT` 占 **8 字节**，指针在 64 位系统下占 **6 字节**，则非叶子节点中一个“主键 + 指针”的索引元组约占 **14 字节**；
  - **单页容纳指针数**：一个 16KB 的非叶子节点可以存储约 $16384 / 14 \approx 1170$ 个指针索引项；
  - 假设叶子节点单行数据记录大小为 **1KB**（常规业务数据），则一个叶子节点数据页可以存放约 $16\text{KB} / 1\text{KB} = 16$ 条记录；
- **总容量计算**：
  - **高度为 2** 的 B+ 树：$1170 \times 16 \approx 18,720$ 条数据（约 1.8 万条）；
  - **高度为 3** 的 B+ 树：$1170 \times 1170 \times 16 \approx 21,902,400$ 条数据（约 **2190 万条**！）；
  - **高度为 4** 的 B+ 树：可容纳百亿级数据。
- **结论**：正因为 B+ 树极高的扇出（Fan-out），只需 **3 次磁盘 I/O（且根节点常驻内存，实际仅需 2 次物理 I/O）** 即可在上千万级大表中精准检索到目标记录。

### Q3: 为什么间隙锁（Gap Lock）之间彼此兼容，却极易引发死锁（Deadlock）？

**标准回答**：
- **间隙锁兼容性设计**：间隙锁的唯一目的就是**“保护区间，阻止其他事务插入”**。因此，多个事务对同一区间加间隙锁（如事务 A 与事务 B 同时持有 `(10, 20)` 的 Gap Lock）是完全兼容的，不会互斥。
- **死锁形成路径**：
  1. 事务 A 执行 `SELECT * FROM t WHERE id = 15 FOR UPDATE;`（记录 15 不存在），事务 A 获得 `(10, 20)` 的 Gap Lock；
  2. 事务 B 同样执行 `SELECT * FROM t WHERE id = 18 FOR UPDATE;`，由于间隙锁彼此兼容，事务 B 同样成功获得 `(10, 20)` 的 Gap Lock；
  3. 事务 A 尝试执行 `INSERT INTO t VALUES (15);`，需要申请插入意向锁，发现被事务 B 的 Gap Lock 阻塞；
  4. 事务 B 尝试执行 `INSERT INTO t VALUES (18);`，同样需要申请插入意向锁，被事务 A 的 Gap Lock 阻塞；
  5. **死锁闭环形成**：两个事务各持有一半资源并等待对方释放，触发死锁检测（Deadlock Detector），InnoDB 强制回滚其中一个事务。

### Q4: Go 生产环境中，`database/sql` 连接池设置如果不当，会引发哪些严重故障？

**标准回答**：
- **故障 1：`MaxOpenConns` 未限制导致 MySQL `Too many connections` 崩溃**：
  - 若不限制最大打开连接数，突发流量到来时每个协程都会开辟一个真实的底层 TCP 连接，瞬间打爆 MySQL 实例的连接上限，导致整个微服务集群被数据库直接拒绝连接。
- **故障 2：`ConnMaxLifetime` 未设置或设置过长导致连接被静默切断**：
  - 云上 RDS、L4 负载均衡（HAProxy/LVS）或 NAT 网关通常配置了空闲超时（如 5~10 分钟自动杀掉无流量 TCP 连接）；
  - 若 Go 连接池不知情，继续复用该连接发送请求，会遭遇 `driver: bad connection` 或 `connection reset by peer` 错误；因此 `ConnMaxLifetime` **必须设置得比中间网络组件的超时时间更短**（推荐 3~5 分钟）。
- **故障 3：`MaxIdleConns` 远小于 `MaxOpenConns` 导致 TCP 频繁重连与 TIME_WAIT 爆炸**：
  - 流量波动时，空闲连接由于超过 `MaxIdleConns` 被立刻断开，新请求到来又被迫发起 TCP 三次握手和身份验证，产生大量高消耗的瞬时短连接。建议将两者设为相等或接近。
