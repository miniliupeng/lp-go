# 专题 02：Redis 高并发架构、分布式锁与一致性大厂高频面试题

---

### Q1: Redis 的跳表（SkipList）底层是如何实现的？为什么不用红黑树或平衡二叉树？

**标准回答**：
- **跳表实现机制**：
  - 跳表是在普通有序单链表的基础上增加了**多级索引层（Multi-level Index）**；
  - 每个节点在插入时，通过抛硬币（概率为 1/4 或 1/2）随机决定其索引层高（最大 32 层或 64 层）；
  - 查询时从最高级索引向前查找，当遇到大于目标值的节点时下降一层继续查找，查找/插入/删除的平均时间复杂度均为 **$O(\log N)$**。
- **为什么不用红黑树（Red-Black Tree）**：
  1. **区间范围查询（Range Query）优势显著**：Redis 的 `ZRANGEBYSCORE` 是极其高频的操作。跳表只需先查到区间下界的叶子节点，然后沿着底层双向单链表直接顺序遍历即可；而红黑树进行范围查询需要频繁的中序遍历递归回溯，实现复杂且开销大。
  2. **并发修改与再平衡（Rebalance）开销低**：红黑树在插入或删除节点时，极易破坏红黑平衡规则，触发多次复杂的左旋、右旋和变色操作，甚至级联调整到树根；而跳表的插入和删除仅涉及相邻节点的指针修改，局部性好，更容易支持并发无锁化改造。
  3. **实现简洁，内存利用率可调**：跳表通过调节概率参数 $p$，可以灵活在内存占用与查询性能之间做权衡。

### Q2: 生产环境使用 Redis 实现分布式锁，Redlock（红锁）算法的争议与缺陷是什么？

**标准回答**：
- **Redlock 机制**：向 $N$ 个（通常为 5 个）彼此独立的 Redis 节点依次申请锁，当在超过半数（$N/2 + 1$）节点上加锁成功且耗时小于锁的有效时间时，才认为加锁成功。
- **分布式系统权威 Martin Kleppmann 对 Redlock 的批评**：
  1. **强依赖物理时钟漂移（Clock Drift）**：若其中某个节点的系统时钟发生了 NTP 突跳或跳变，会导致锁提前自动过期被释放，从而违反互斥性。
  2. **长垃圾回收停顿（GC Pause）与系统暂停（Process Pause）**：如果持有锁的客户端在获得锁后发生了几十秒的 Full GC 或虚拟机停顿，其持有的锁在 Redis 侧早已超时，其他客户端会成功拿到锁，此时两个客户端同时操作共享资源导致并发冲突。
- **工业界权衡与最佳实践**：
  - 大厂在大部分常规业务场景中，使用**单主节点 Redis（带哨兵/集群）+ Lua 脚本校验 + Watchdog 看门狗**即可满足 99.9% 的需求；
  - 对数据一致性要求极其严苛的金融计费交易场景，推荐使用 **ZooKeeper / etcd（基于 Paxos/Raft 强一致性共识算法）** 或在数据库层配合 **乐观锁版本号（CAS）**。

### Q3: 为什么说“先删缓存再写库”是大忌？延迟双删又存在什么缺陷？

**标准回答**：
- **先删缓存再写库的致命并发时序**：
  1. 请求 A（写）：先删除了缓存 Key；
  2. 请求 B（读）：并发到来，发现缓存为空，向底层 MySQL 发起读取，读到了**旧值**；
  3. 请求 B（读）：将读取到的旧值重新写入 Redis 缓存；
  4. 请求 A（写）：将新值写入 MySQL；
  - **结果**：**Redis 缓存中永久驻留了旧脏数据！** 只要该 Key 没有设置过期时间，后续所有用户都会读取到脏数据。
- **延迟双删的痛点**：
  - 所谓的延迟双删是在写完库后再休眠几百毫秒（例如 `Sleep(500ms)`）再次删除缓存；
  - **弊端**：休眠的 $N$ 毫秒在复杂的生产分布式网络中根本**无法精准确定**！若遇到读请求执行较慢、或者 MySQL 主从同步延迟（Replication Lag）超过了该休眠时间，延迟双删依然无法清除在从库上读取并回填的旧数据，并且同步休眠会极大损耗写入吞吐。

### Q4: Go 的 `singleflight` 内部是如何处理 panic 和超时的？

**标准回答**：
- **Panic 共享保护**：在官方 `golang.org/x/sync/singleflight` 实现中，如果第一个真正发起回源的协程抛出了 `panic`，`singleflight` 会使用 `recover` 捕获该 panic，并把它包装为一个特殊的内部错误，确保**其他并发等待结果的协程不会发生死锁或崩溃**，最后再重新抛出该 panic。
- **超时与短路泄露风险**：
  - 若第一个执行回源的协程因为下游网络无超时挂起，所有后续共享的协程都会永久停留在 `c.wg.Wait()`；
  - **最佳实践**：在业务逻辑中，传入 `singleflight` 的函数必须带上 **`context.WithTimeout`**，并且可以配合 `DoChan` 异步返回 channel，支持外部调用方自主 select 超时放弃等待。
