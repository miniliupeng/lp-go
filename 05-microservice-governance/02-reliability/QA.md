# 专题 02：微服务高可用治理高频面试题 (QA)

### Q1：令牌桶（Token Bucket）与漏桶（Leaky Bucket）的核心区别是什么？为什么大厂通常选用令牌桶？
**标准深度解析**：
1. **原理差异**：
   - **漏桶**：流入水流速率任意，但流出水滴速率严格恒定。强行平滑所有流量，超出容量则溢出丢弃。
   - **令牌桶**：匀速向桶中生成令牌，请求消费令牌。若桶中有存量令牌，允许瞬间并发全额消耗。
2. **为什么大厂偏好令牌桶**：互联网真实流量往往具有高突发性（如整点秒杀、大促开抢）。漏桶会将突发的合法流量全部排队延迟或丢弃，体验极差；而令牌桶在保障长期平均速率受控的前提下，**允许瞬时突发流量快速通过**。标准库与知名开源库（如 `golang.org/x/time/rate`）均采用令牌桶模型。

### Q2：断路器在半开（Half-Open）状态下，若突发大量请求，应该全部放行还是限制放行？
**标准深度解析**：
1. **必须严格限流/少量放行**：半开状态的本质是“探测下游服务是否已经从故障或过载中完全复苏”。如果直接全部放行，故障刚刚恢复的脆弱下游会瞬间再次被瞬时洪峰打崩，导致熔断器反复在 Open 和 Half-Open 之间剧烈震荡。
2. **工程实现**：半开状态通常只允许极少数探测请求（如 1~3 个或者总流量的 1%）通行。只有当这些探测流量连续成功且延迟符合预期，熔断器才真正闭合（Closed）。

### Q3：高并发写场景下，前端连续快速点击“提交订单”，如何保证业务只扣一次款（幂等性）？
**标准深度解析**：
1. **Token 预下发机制**：用户打开页面时，由后端生成全局唯一的一次回话 Token（如 UUID 或分布式 ID）并存入 Redis。
2. **提交时原子判定**：前端提交订单携带此 Token。后端通过 Redis `SET token value NX PX 30000` 进行原子抢占：
   - 若抢占失败（返回 nil），说明正在处理或已处理，直接返回“请求正在处理中，请勿重复提交”；
   - 若抢占成功，执行业务（开启事务、扣库存、创建订单）。
3. **状态回调与更新**：业务执行成功后，将订单号与执行结果关联持久化，并将 Token 状态标记为已完成。若业务失败且允许重试，需及时释放锁或清理 Token。
