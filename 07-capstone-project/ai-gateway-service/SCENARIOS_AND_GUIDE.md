## 🌐 一、 业务定位：它到底处于系统中的什么位置？

形象地说，`ai-gateway-service` 就是**企业级大模型与 AI 算力集群的“智能海关、防弹衣与总调度器”**。

在 2026 年的企业技术架构中，企业往往接入了多种大模型（如自建的 DeepSeek、vLLM、Ollama，或者公有云的 OpenAI、Claude）。
**网关处于所有前端应用（Web、小程序、手机 App、企业内部飞书/钉钉机器人）与底层昂贵大模型集群的正中间**：

```text
[ 前端 Web / App / 业务系统 ]
              │
              ▼ (统一协议: /v1/chat/completions)
┌────────────────────────────────────────────────────────────┐
│      AI-Gateway-Service (高性能智能网关 - 拦截把关)        │
│                                                            │
│  [安全防线] API-Key 租户鉴权 ──> 令牌桶限流 ──> 自适应熔断   │
│  [性能优化] SingleFlight 并发防击穿 ──> fmt.Appendf 零拷贝  │
│  [精准生成] 私域向量 RAG 检索增强 (消除模型幻觉)           │
│  [流式反压] SSE 有界推流管道 (防 OOM) ──> ctx.Done() 级联取消│
│  [可观测性] W3C TraceID 链路贯穿 ──> Prometheus RED 指标   │
└────────────────────────────────────────────────────────────┘
              │
              ▼ (受控的健康流量)
[ 上游模型集群 (DeepSeek / vLLM / OpenAI / 私有 GPU 集群) ]
```

## 💣 二、 生产场景深度拆解：如果没有网关，会发生什么灾难？

如果让前端或业务服务**直接裸连大模型**，在工业级生产中必然发生以下 5 大灾难性事故，而网关正是这 5 大灾难的“终结者”：

### 1. 流量击穿与 GPU 显存打爆
- **线上灾难**：某热点事件爆发，1 万个用户几乎在同一秒询问同一个问题。如果直接打到上游大模型，上万个请求同时在 GPU 显卡中创建解码 Context，瞬间导致显存爆满（OOM）服务瘫痪。
- **网关解法**：
  - **令牌桶限流（RateLimiting）**：超出租户配额的突发请求直接在网关层返回 429，根本不浪费上游一滴 GPU 算力；
  - **SingleFlight 并发合并**：将瞬时相同的万级 Prompt 合并为 1 次底层推理，其余 9999 个请求共享结果，节省 99.9% 算力。

### 2. 模型回答“一本正经地胡说八道”（幻觉事故）
- **线上灾难**：用户询问“我们公司差旅报销标准是多少？”，通用大模型训练集里没有企业私有信息，会编造出完全虚假的数据导致企业损失。
- **网关解法**：
  - **私域 RAG 检索增强**：在网关内部毫秒级（纯 Go 余弦计算仅 1.9μs）从本地向量库与 BM25 词频库召回企业专有制度文档，动态拼入 Prompt，把“开卷考试资料”给到模型，彻底消除幻觉。

### 3. 弱网客户端把网关内存撑爆（流式 OOM 陷阱）
- **线上灾难**：上游大模型吐字飞快（每秒 80 个 Token），但某个移动端用户处于地下车库弱网环境，几秒钟才接收一个字符。如果网关无脑用无界通道缓存，成千上万个弱网连接会导致几 GB 的 Token 堆积在网关内存中，最终触发 Linux OOM Killer 杀掉进程。
- **网关解法**：
  - **有界 Channel + 超时反压（Backpressure）**：严格限制通道容量，下游超过 100ms 不取走数据直接触发反压机制断流，彻底保住服务器内存。

### 4. 客户端关掉页面，后台还在疯狂“烧钱”
- **线上灾难**：大模型生成一篇长文章需要 40 秒。用户看了 2 秒觉得不满意，随手关掉了浏览器标签页。如果网关没有感知能力，上游推理集群会继续全功率运行剩下的 38 秒，每天白白烧掉几万甚至几十万 Token 费用。
- **网关解法**：
  - **级联取消机制**：监听 `r.Context().Done()`。一旦用户断网或关闭网页，网关即刻切断与上游的 TCP 连接，上游模型感知到连接中断立即中断 GPU 推理，真正做到“用户走，计费停”。

### 5. 跨系统链路排查“两眼一抹黑”
- **线上灾难**：前端报错“生成超时”，但后端日志几百万条，根本不知道对应哪条数据库日志或模型报错。
- **网关解法**：
  - **W3C `traceparent` 全链路贯穿**：网关自动注入 TraceID，结构化日志（slog）与下游各层调用全部携带该 ID，输入一个 TraceID 即可秒级还原全链路耗时。

## 💻 三、 本机 1 分钟实战体验指引

本项目在本地完全自闭环（无需安装 Docker、无需显卡、无需配置复杂的外部服务，内置了高性能纯 Go 向量引擎与仿真推理系统）。

### 步骤 1：启动网关服务
在项目根目录下打开终端，执行：
```bash
go run ./05-capstone-project/ai-gateway-service/cmd/gateway/main.go
```
看到如下日志说明网关已在本地 `8090` 端口就绪：
```json
{"time":"...","level":"INFO","msg":"gateway server started successfully","addr":":8090"}
```

---

### 步骤 2：实操体验 1 —— 发起 SSE 流式打字机交互（开启 RAG 私域知识增强）
打开**新的终端窗口**，使用 `curl -N`（禁用缓冲）发起提问：

```bash
curl -N -X POST http://127.0.0.1:8090/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer sk-production-ai-gateway-key-9527" \
  -d '{
    "model": "deepseek-r1-chat",
    "messages": [
      {"role": "user", "content": "请告诉我网关的反压机制"}
    ],
    "stream": true,
    "enable_rag": true
  }'
```

**你看到的实际效果**：
- 屏幕上会像真正的 ChatGPT / DeepSeek 一样，**逐字逐句流式吐出 Token**；
- 并且你会发现，回答内容中自动融合了我们预置在网关本地知识库中的《网关高可用手册》内容！

---

### 步骤 3：实操体验 2 —— 查看实时 Prometheus 监控大盘与首字延迟 (TTFT)
在终端执行：
```bash
curl http://127.0.0.1:8090/metrics
```
**返回实时数据**：
```json
{
  "total_requests": 1,
  "total_errors": 0,
  "error_rate_pct": 0,
  "avg_ttft_ms": 11.25,
  "p99_duration_ms": 165.40
}
```
> **核心指标解读**：
> - `avg_ttft_ms`：首字响应延迟（Time To First Token），大模型时代衡量网关推流性能的最关键指标。

---

### 步骤 4：实操体验 3 —— 验证生产级优雅停机（Graceful Shutdown）
切回正在运行网关的第一个终端窗口，按下 **`Ctrl + C`**：

**你看到的日志**：
```text
{"level":"INFO","msg":"shutting down gateway server gracefully..."}
{"level":"INFO","msg":"gateway server exited cleanly, all active connections drained"}
```
网关没有直接粗暴闪退，而是启动了平滑排空机制，等待所有活跃连接将数据完整推送完毕后安全退出！
