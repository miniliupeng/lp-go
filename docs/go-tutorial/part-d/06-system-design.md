# 06 系统设计题里的 Go 落地

这一章用一个进程内短链说明：设计题要落到数据结构、并发、过期和失败，而不是只画方框。实现是 [shorturl](../examples/partd/shorturl/short.go)。

## 短链

`Put` 给 URL 分配短码，`Resolve` 换回来。

现在的实现：

- 短码是递增计数的 62 进制。测试能看懂下一个码是什么。线上应改成随机或哈希，冲突时重试。递增计数会暴露生成顺序。
- 同一 URL 在未过期时返回原来的短码，所以重复提交不会制造一串新码。
- `ttl > 0` 时记录到期时间。`Put` 和 `Resolve` 都会先丢掉已到期的记录。到期后再 `Put` 同一个 URL，会得到新短码。
- 全部状态在一把 `Mutex` 后面。读多写少时可以换成 `RWMutex`，但过期删除是写，要避免在读锁下删除。

它没有持久化，进程一退数据就没了。设计题里下一步是：短码到 URL 的存储用数据库唯一约束防冲突；热门短码用带 TTL 的缓存；缓存未命中用 [singleflight](03-cache-ratelimit.md) 合并。

## 设计题要主动说的边界

**短链**

- 码的长度和冲突概率。62 进制 6 位大约是 568 亿，仍然要处理冲突。
- 过期后码能不能立刻给别人。本实现过期即删，码的计数还在涨，短时间不会复用刚过期的递增码；随机码则必须避免把刚过期的码立刻发给另一个 URL。
- 跳转用 302，缓存头决定浏览器会不会记住。这是 HTTP 语义，不是 map 的语义。
- 恶意 URL：存之前做校验，跳转时不要把内部错误原文回给用户。

**限流服务**

- 令牌桶放在哪：网关进程内是单机限额；全局限额要有一个共享计数。共享计数用 Redis 加原子操作，并接受时钟和网络失败时的策略（失败开放还是失败关闭）。
- 见 [限流一章](03-cache-ratelimit.md) 的单机桶。不要把单机桶说成全局限流。

**任务队列**

- 至少一次投递意味着消费者要幂等。用任务 id 做去重表，处理完再确认。
- 消费者看 `context`。进程 `Shutdown` 时停止取新任务，把已经取到的任务处理完或把可见性超时交还给队列。
- 并发度用带缓冲的 channel 当信号量：缓冲容量就是同时执行的上限。内存模型允许用它做计数信号量，见 [内存一章](../part-c/01-memory-escape.md)。

**上传或写接口**

- body 用 `MaxBytesReader` 限制大小。
- 写盘路径用 `os.Root` 限制在一个目录里，见 [JSON 与文件](../part-b/01-cli-files-json.md)。
- 超时用 `ReadHeaderTimeout`，不要用一个很短的 `ReadTimeout` 把合法的大 body 掐掉。见 [net/http](01-net-http.md)。

## 运行

```bash
go test ./docs/go-tutorial/examples/partd/shorturl -count=1
```

## 面试时的结构

用四句话：数据怎么放、并发怎么保护、失败和过期怎么处理、什么是这版实现故意没做的。最后一句能挡住大部分追问。本短链故意没做的是持久化、随机短码和跨进程限额。
