# D3 缓存与限流

三个词指的是不同故障。实现都在 [examples/d3limit](../../../examples/d3limit/limit.go)，时钟由测试注入。Redis 是这些策略常驻的地方。本仓库没有连接 Redis，后半是协议和数据结构上的概念，用来回答设计题。

## 这一章你要会什么

能区分击穿、穿透和雪崩，能按测试讲清令牌桶和 singleflight 的边界，能说出缓存怎么和数据库配合，以及分布式锁要拿什么当凭证。

## 三种故障

- **击穿**：热点键失效的瞬间，很多请求一起打到数据库。
- **穿透**：这个键本来就不存在，每次都穿过缓存。
- **雪崩**：大量键同时失效，或者缓存整体不可用。

`singleflight` 只合并「同一个 key 上还在执行的那一次调用」。函数返回后 map 里的记录被删掉，下一次会再执行。它不保存上一轮结果。所以它挡住的是同一时刻的并发，不是下一秒的新请求。击穿还要靠 TTL 和限流一起看。

穿透用很短的负缓存：确认没有这个键之后，缓存「没有」这个事实，TTL 用秒级，不要用小时。数据库故障不能缓存成「没有」，否则故障期间的键都会被记成不存在。

雪崩靠过期时间加抖动，避免同一分钟创建的键在同一分钟一起过期。缓存整体不可用时，入口要限流或降级，而不是让所有请求同时打到数据库。示例没有做抖动。

## 进程内的缓存和桶

`TTLCache` 在一把 `Mutex` 后面。`Get` 在 `now` 不再早于 `expires` 时视为未命中，到期时刻本身算过期。负缓存表示「确认没有」。`sync.Pool` 不是缓存，见 [同步与原子](../运行时/C5-同步与原子.md)。

`Allow` 按流逝时间补充 `elapsed * rate`，不超过 `burst`，再尝试取走 1 个。时间不前进就不补充，所以同一时刻最多通过 `burst` 次。测试里 `rate` 是 10、`burst` 是 2：起点过两次，第三次失败；100 毫秒后按每秒 10 个补充 1 个。

这是单机桶。多副本时每个进程各有一桶，总流量大约是副本数乘 `rate`。全局限额要有共享计数。生产实现常用 `golang.org/x/time/rate`。本教程的桶把规则写短，方便测试，没有实现 `x/time` 的全部 API。

## singleflight

`Group.Do` 里，后来的调用等待同一次 `WaitGroup`。`testing/synctest` 能等到这 8 个 goroutine 都堵在可等待的阻塞上，此时函数体只计数 1 次。放开之后再调一次，计数变成 2，说明结果没有被留成缓存。

`fn` 不能 panic。panic 发生在 `Done` 之前时，等待者会一直堵着。调用方要在 `fn` 里把 panic 转成 `error`。

`Do` 的返回值会分给等待的所有人。里面如果是指针，调用方不要各自修改。要改就先复制。

```bash
go test ./examples/d3limit -count=1
```

## 和数据库怎么配合

读路径常用 cache-aside：先读缓存，未命中再读数据库，再把结果放进缓存。写路径先写数据库，成功后删除缓存，而不是先改缓存。先改缓存再写库，写库失败时缓存里是一个从未提交的值。

删除缓存和读的并发仍会交错：读请求在删除之前把旧值又写回缓存。要缩短这个窗口，可以在写完之后再删一次，第二次放在短暂延迟之后。这仍然不是形式化的证明。要求强一致时，读要走到数据库，或者用版本号拒绝旧的回填。

缓存里的值要有自己的结构，包含数据，而不是只存一个裸字符串却说不清过期时间。过期以缓存系统的 TTL 为准，应用再做一次判断可以挡住时钟偏差，但两套过期要写明谁说了算。

## Redis 上要知道的概念

Redis 的键通常对应一种类型：字符串、哈希、列表、集合、有序集合。哈希适合一个对象的多个字段。有序集合按分数排序，适合排行榜。列表按插入顺序，适合简单队列，不适合需要确认和重试的消息，那种情况用后面 [熔断](D4-熔断重试与可观测性.md) 里的消息模型。

小对象的底层编码会变。Redis 7 起，原先用 ziplist 的多种小对象改用 listpack。这是内存布局，不改变你用的命令的语义。大键（一个值有几兆，或一个哈希有上百万字段）会让删除、复制和网络传输卡住。热键是所有请求都打在一个键上，副本和分片都帮不上这个键。热键要拆开，或者在应用侧做本地缓存。

分布式锁如果用 Redis，凭证是一个随机 token，而不是「键在不在」。获取用 `SET key token NX PX ttl`：不存在才设置，并带过期。释放时比较 token 再删除，用一段 Lua 在服务端原子完成。直接 `DEL` 会把别人刚拿到的锁删掉。过期时间要大于临界区，临界区还要看锁是不是已经过期，过期之后不要再写。单实例 Redis 上的这把锁，在主从切换时可能丢。多主协议（Redlock）有公开的争议，回答时说出「单实例锁在故障切换时可能两个客户端同时认为自己持有」，比背一个有争议的协议更稳。

本仓库没有 Redis 客户端，上面的命令不要当成已经测过的代码。

## 对比陷阱

| 说法 | 实际情况 |
| --- | --- |
| singleflight 等于缓存 | 调用结束后记录被删，下一次会再执行 |
| 负缓存可以设一天 | 穿透保护用很短的 TTL。故障不能记成「没有」 |
| 令牌桶的 `rate` 是全局的 | 示例是单机桶。副本数会放大总速率 |
| 先更新缓存再写数据库 | 写库失败时缓存里是脏值。先写库，再删缓存 |
| 锁用 `SETNX` 再另设过期 | 两步之间进程死掉，键会没有过期。用一条带 `PX` 的 `SET` |
| 释放锁就是 `DEL` | 可能删掉别人的锁。比较 token 再删 |
| `sync.Pool` 可以做这章的 TTL | 池里的对象会被 GC 清掉 |

## 练习

1. 把 `burst` 改成 1，预测起点第二次 `Allow` 的结果，再改测试，然后改回 2。
2. 给 `TTLCache` 写一个负缓存用例：`Put` 一个「没有」的标记，TTL 内 `Get` 命中，到期时刻 `Get` 未命中。到期时刻的比较已经在现有测试里，读一遍条件。
3. 用文字写出获取锁和释放锁的两步，标明 token 在哪一步被比较。

## 面试延伸

三种故障各用一句，并配上本示例真正做了的事：singleflight 合并在途的一次，负缓存要短，桶的突发是 `burst`，多副本不是全局限流。一致性说 cache-aside：读未命中再填，写库成功后删缓存，并承认回填会把旧值写回去。Redis 锁说 `SET NX PX` 加 token，释放要比较再删，主从切换时单实例锁可能失效。不要报一个没跑过的 Redis QPS。

## 问答题

### 问：三种故障各用一句，示例各做了哪一件？

击穿是热点失效时一起打到数据库，singleflight 合并同一次在途调用。穿透是键本来不存在，用很短的负缓存。雪崩是大面积同时失效，靠过期抖动和入口限流。示例没有做抖动。

### 问：singleflight 为什么不是缓存？

`fn` 返回后 map 里的记录被删掉。`synctest` 里 8 个 goroutine 只计数 1 次，放开后再调一次变成 2。它不保存上一轮结果。`fn` 不能 panic，否则等待者一直堵着。返回的指针不要让每个调用方各自修改。

### 问：令牌桶的测试数字？

`rate` 是 10，`burst` 是 2。起点过两次，第三次失败。时间不前进就不补充。100 毫秒补充 `0.1 * 10 = 1` 个。这是单机桶，副本数会放大总速率。全局限额要共享计数。生产常用 `golang.org/x/time/rate`，教程里的桶是为了把规则测清楚。

### 问：到期时刻本身算命中吗？

不算。`Get` 在 `now` 不再早于 `expires` 时视为未命中。负缓存表示确认没有，TTL 用秒级。数据库故障不能记成「没有」。`sync.Pool` 不是这种缓存。

### 问：先改缓存还是先写库？

先写库，成功后删缓存。先改缓存再写库，写库失败时缓存里是从未提交的值。删缓存和读并发时，读请求可能把旧值又填回去。要求强一致时读数据库，或用版本号拒绝旧的回填。

### 问：Redis 的锁为什么不能 `DEL`？

凭证是随机 token。获取用一条 `SET key token NX PX ttl`，不存在才设置，并带过期。分两步 `SETNX` 再设过期，进程死在中间就会留下没有过期的键。释放时比较 token 再删。直接 `DEL` 会删掉别人刚拿到的锁。

### 问：主从切换时这把锁还在吗？

单实例上的锁可能在切换时丢，两个客户端同时认为自己持有。临界区要能容忍这个窗口，或者不要在过期之后继续写。多主协议有公开争议，回答时把这个窗口说出来即可。本仓库没有 Redis 客户端。

### 问：热键和大键差在哪？

热键是所有请求打在一个键上，加副本也帮不上这一把。大键是一个值太大或字段太多，删除和复制会卡住。Redis 7 起，原先用 ziplist 的多种小对象改用 listpack，这是内存布局，不改变命令的语义。列表不适合需要确认和重试的消息。
