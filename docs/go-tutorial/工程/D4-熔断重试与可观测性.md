# D4 熔断、重试与可观测性

示例在 [examples/d4svc](../../../examples/d4svc/breaker.go)。限流的令牌桶在 [缓存与限流](D3-缓存与限流.md)。context 的取消在 [上下文与日志](../能写服务/B2-上下文与日志.md)。内存指标的定义在 [垃圾回收](../运行时/C3-垃圾回收.md)。

本仓库没有 Kafka、没有 gRPC 服务。这一章后半把消息投递、超时预算和 RED 指标讲清楚，方便设计题，不附带没跑过的吞吐数字。

## 这一章你要会什么

能按关闭、打开、半开讲完熔断器，知道哪些操作可以重试，能说明至少一次投递为什么要求业务幂等，能选用 RED 而不是用平均数描述延迟。

## 重试预算

只重试幂等操作，或者带幂等键的写。幂等是指同一个请求执行一次和执行多次，业务结果相同。`GET` 一般可以重试。扣款、下单如果没有幂等键，重试会做两次。

重试次数要算进入口的 context 截止时间。时间到了就停，不要为了再试一次去用 `context.Background()`。下一次重试之前留出间隔，并加上抖动，避免所有客户端在同一毫秒一起重试。间隔的上限受剩余时间约束：剩余时间不够一次调用，就不再发。

调用下游时把剩余时间传下去。gRPC 和 `net/http` 都用 context 的截止时间。入口给 300 毫秒，入口自己已经用了 100 毫秒，下游的 context 只剩 200 毫秒。下游再调用更下游时继续传递，而不是每层都重新给 300 毫秒。每层都重给满额，用户侧的超时到了，内部还在继续做。

## 熔断

`Breaker` 有三个状态，测试用注入的时钟，阈值 2、冷却 1 秒：

- **关闭**：请求通过。连续失败达到阈值后打开。
- **打开**：冷却结束前拒绝。`now` 不再早于 `openUntil` 时，下一次 `Allow` 进入半开并放行一个探测。
- **半开**：同时只放一个探测。探测失败会重新打开，冷却从当前时间再算。探测成功调用 `Success` 后回到关闭，失败计数清零。

它不区分 4xx 和 5xx。参数错误重试也不会成功，不应当算进「下游不健康」。讲这个状态机时把「还没做错误分类」一起说。生产里通常只把超时、连接失败和 5xx 计为失败。

半开如果把流量全放过去，下游刚恢复又会被打满。所以探测是一个，成功后再关闭熔断，让正常流量进来。

```bash
go test ./examples/d4svc -count=1
```

## 日志和指标

JSON `slog` 在 Info 级别下会记下 `msg` 和 `port`，不会出现 Debug 的 `hidden`。`Enabled(ctx, LevelDebug)` 为 false。参数在调用前就会求值，热路径先看 `Enabled`。

`runtime/metrics` 读取 `/memory/classes/total:bytes` 和 `/memory/classes/heap/released:bytes`。前者在正常进程里是非零的 `uint64`。名字写错时 `Kind` 是 `KindBad`，这时不能调用 `Uint64()`。两者相减就是内存软上限使用的那组量。不要用会 STW 的 `ReadMemStats` 做高频采集。

服务的黄金信号用 RED：速率（Rate）、错误（Errors）、耗时（Duration）。延迟看分位数，例如 99 分位。平均数会被大量很快的请求拉低，看不出慢的那一部分。资源用 USE：利用率、饱和度、错误。CPU 打满是利用率，队列变长是饱和度。

跟踪把一个请求在多个服务里的片段串起来。片段之间用 context 里的跟踪号传递，日志里打同一个号。没有这个号，只能按时间对日志。`pprof` 端点能看到栈和堆，不要挂到公网。`goroutineleak` 能发现什么，见 [接口、反射与剖析](../运行时/C6-接口反射与剖析.md)。

## 消息投递

常见的投递语义：

| 语义 | 含义 | 你要额外做什么 |
| --- | --- | --- |
| 至多一次 | 可以丢，不重复 | 发送失败就放弃 |
| 至少一次 | 不丢，可能重复 | 消费端按业务键去重 |
| 恰好一次 | 在某个范围内只处理一次 | 范围要说清。端到端仍要业务幂等 |

Kafka 一类日志通常按分区保序，分区内的记录有偏移。消费者处理成功后再提交偏移，崩溃时从上一次提交的偏移重来，这是至少一次：处理完、提交前崩溃，这条会再来一次。先提交再处理，崩溃会丢。幂等做法是业务唯一键加一张去重表，或者让写入本身带条件（只插入一次）。

生产者把确认设成要等足够多的副本，并打开幂等生产者，减少发送重试造成的重复。这降低丢失和重复，不代替消费端的业务键。

KRaft 把集群元数据放在 Kafka 自己的仲裁里，不再依赖 ZooKeeper。这是部署形态。它不改变「分区内有序、提交偏移之前可能重复」这两条。

积压是生产速度持续高于消费速度。消费者的个数可以加到分区数，再多没有分区给它们。处理变慢时先看单条耗时和下游，而不是只加分区。

本仓库没有 Kafka。上面是协议层面的设计，不要写成「测试已经投递了多少条」。

## 对比陷阱

| 说法 | 实际情况 |
| --- | --- |
| 失败就重试，重试用新的 `Background` | 非幂等会重复执行。超时要用入口剩下来的时间 |
| 半开状态把所有流量放行 | 示例只放一个探测。失败再打开 |
| 4xx 也计成熔断失败 | 示例没分类。参数错误说明不了下游宕了 |
| 延迟看平均数 | 快请求会把平均数拉低。看分位数 |
| 先提交消息偏移再处理 | 处理前崩溃就丢。至少一次是处理成功后再提交，并接受重复 |
| 打开了生产者幂等就端到端只处理一次 | 消费端仍可能重复。业务键还要有 |
| `ReadMemStats` 做高频指标 | 会 STW。用 `runtime/metrics` |

## 练习

1. 把阈值改成 1，写出第一次 `Failure` 之后、冷却结束之前 `Allow` 的返回值。
2. 给一次重试写出时间预算：入口剩余 50 毫秒，下游一次调用需要 80 毫秒。说明为什么不该发出这次调用。
3. 用业务键写一句去重规则：同一键的写入只保留第一次的结果。标明这是至少一次投递下的消费端责任。

## 面试延伸

熔断按三个状态和「半开一个探测」来讲，并说明示例不区分 4xx。重试讲幂等、剩余时间和抖动。指标讲 RED 和分位数，内存用两个 metrics 名字相减。消息讲至少一次等于「可能重复」，偏移在处理成功后提交，幂等键在业务侧。KRaft 只说元数据不再放在 ZooKeeper。不报没测过的吞吐。

## 问答题

### 问：阈值 2、冷却 1 秒时，状态怎么走？

关闭状态下连续失败两次后打开。冷却结束前 `Allow` 拒绝。`now` 不再早于 `openUntil` 时，下一次放行一个半开探测。探测失败重新打开，冷却从现在再算。探测成功才回到关闭，失败计数清零。

### 问：为什么半开只放一个？

刚恢复的下游再被全部流量打满，会立刻又失败。一个探测成功，再把熔断关掉。示例不区分 4xx 和 5xx。参数错误重试也不会成功，生产里通常只把超时、连接失败和 5xx 计为失败。

### 问：什么可以重试？

幂等操作，或带幂等键的写。重试使用入口 context 剩下来的时间。剩余时间不够一次调用，就不要发。每层把剩余时间往下传，不要每层重新给满。间隔加抖动，避免所有客户端同一毫秒一起重试。不要为了再试一次换成 `context.Background()`。

### 问：至少一次为什么还会重复？

处理成功、提交偏移之前崩溃，这条会再来。先提交再处理，崩溃会丢。消费端用业务唯一键拒绝第二次写入。生产者的确认和幂等生产者减轻丢失和重复，不代替这个业务键。

### 问：KRaft 改变了投递语义吗？

没有。它把集群元数据放在 Kafka 自己的仲裁里，不再依赖 ZooKeeper。分区内仍然有序，偏移仍然是消费进度。积压时消费者最多加到分区数。本仓库没有 Kafka，不要报吞吐。

### 问：RED 和平均数？

速率、错误、耗时。延迟看 99 分位。平均数会被大量快请求拉低。资源用 USE：利用率、饱和度、错误。跟踪号放在 context 里，日志打同一个号。

### 问：内存指标的两个名字？

`/memory/classes/total:bytes` 减去 `/memory/classes/heap/released:bytes`。前者在正常进程里非零。名字写错是 `KindBad`，不能 `Uint64()`。`ReadMemStats` 会 STW。Info 级别的 `slog` 不会出现 Debug 才有的字段，但参数在调用前就会求值。

### 问：pprof 为什么不对公网？

它能看到栈、堆和运行中的 goroutine。加上认证，采完就停。CPU 剖面本身有开销。`goroutineleak` 的定义在 [接口、反射与剖析](../运行时/C6-接口反射与剖析.md)。
