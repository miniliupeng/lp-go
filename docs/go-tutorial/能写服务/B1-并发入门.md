# B1 goroutine、channel 与 WaitGroup

`go f()` 启动一个 goroutine。它和当前函数并发执行。函数返回不会等待它。操作系统线程、网络轮询器和抢占放在 [调度器](../运行时/C2-调度器.md)。channel 的关闭和 `hchan` 放在 [通道与选择](../运行时/C4-通道与选择.md)。示例在 [examples/b1conc](../../../examples/b1conc/conc.go)。

## 这一章你要会什么

会用 channel 交回固定个数的结果，会用 `WaitGroup` 等待一组 goroutine，知道共享变量要加锁，能说出 `go` 语句建立了哪一种 happens-before。

## goroutine 不是线程

goroutine 由运行时调度到线程上。启动一个 goroutine 只分配一小段初始栈，栈会按需增长。所以「每个请求一个 goroutine」在 Go 服务里是常态。它仍然有成本：每个堵着不返回的 goroutine 都占着栈，请求取消之后还不退出，就是泄漏。

`go` 语句的执行 happens before 新 goroutine 开始。启动之前写入的变量，新 goroutine 能看见。goroutine 退出本身不建立同步。它在退出前写的变量，别的 goroutine 不一定看得见，除非中间有 channel 收发、`WaitGroup` 的 `Wait` 返回、锁，或原子操作。内存模型的条目在 [内存与逃逸](../运行时/C1-内存与逃逸.md)。

主 goroutine 从 `main` 返回时，进程退出，其它 goroutine 被直接停掉，defer 也不再跑。后台任务要在 `main` 里等到结束，或者随进程退出是你接受的。

## 用 channel 收集结果

`SumSquares(4)` 启动 4 个 goroutine，每个把 `i*i` 送进同一个 channel。主 goroutine 接收恰好 4 次，所以不需要 `close`。Go 1.22 起每次迭代有自己的 `i`，闭包里的 `i` 是当次的值。1 到 4 的平方和是 30。参数是 0 时一次也不接收，返回 0，不会卡在接收上。

无缓冲 channel 的发送和接收要配对。谁先到，谁等待。发送完成意味着接收方已经拿走值。有缓冲时，缓冲没满就可以先发送，接收方稍后取。容量怎么变成信号量，见 C1。

把 channel 变量设成 nil 之后，对它发送或接收会永远阻塞。放在 `select` 的 case 里时，这个 case 永远不会被选中。这可以用来在循环里「关掉」一支 case：把那个 channel 变量赋成 nil，而不是再维护一个布尔值。

`First` 在数据和停止两个 channel 里取一个。测试每次只让其中一个就绪。两个都就绪时，规范要求用均匀的伪随机选一个，测试不能断言一定走哪边。

关闭规则先记三条，细节在 C4：

- 只由发送方，或唯一负责关闭的那一方，关闭 channel。
- 向已关闭的 channel 发送会 panic。
- 接收方在取空之后得到零值和 `ok == false`。

## WaitGroup

`SumSquaresLocked` 用 `sync.WaitGroup`。Go 1.27.1 的 `WaitGroup.Go(f)` 会 `Add(1)`，`f` 正常返回后 `Done`。文档要求 `f` 不要 panic。源码里如果 `f` panic，会把 panic 重新抛出，并且故意不调用 `Done`，避免 `Wait` 先返回、进程在 panic 完成前退出。要在任务里接住 panic，就在 `f` 自己的 defer 里处理，让 `f` 正常返回。

手写的配对是：

```go
var wg sync.WaitGroup
wg.Add(1)
go func() {
    defer wg.Done()
    work()
}()
wg.Wait()
```

`Add` 要发生在 `Wait` 可能看到 0 之前。在子 goroutine 里面 `Add`，主 goroutine 可能已经 `Wait` 完并离开了。计数已经是 0 时再 `Add` 一个正数，配不上这一次已经返回的 `Wait`。`Add` 一个负数把计数减到 0 以下会 panic。

## 共享变量

累加共享变量 `sum` 时用 `Mutex`。没有这把锁，两个 goroutine 同时 `sum +=` 就是数据竞争。数据竞争的程序没有顺序一致性的保证，结果可以是任何值，也可以让程序在别的地方看起来「不可能」地出错。

`go test -race` 能抓住测试正好撞上的这种写。它给内存访问插桩，漏掉的路径它看不见。竞态检测使测试变慢，CI 里对并发包单独跑是值得的。

能用 channel 把结果交回主 goroutine 时，就不必再共享 `sum`。`SumSquares` 是这种写法。`SumSquaresLocked` 是为了把锁和 `WaitGroup` 放在同一个例子里。

## 对比陷阱

| 写法 | 实际结果 |
| --- | --- |
| `go` 之后立刻读子 goroutine 写的变量，中间没有同步 | 不保证看得见。退出不同步 |
| `main` 返回时期待后台 defer 做清理 | 进程退出，那些 defer 不跑 |
| 在子 goroutine 里 `WaitGroup.Add` | `Wait` 可能已经返回 |
| `WaitGroup.Go` 的函数 panic | panic 被重新抛出，并且不调用 `Done` |
| 两个 goroutine 对同一个 map 一个读一个写 | panic。见 [类型](../地基/A3-类型.md) |
| 两个 `select` case 都就绪，断言会走写在前面的那个 | 伪随机，不能断言顺序 |

## 运行

```bash
go test ./examples/b1conc -count=1
go test -race ./examples/b1conc -count=1
```

## 练习

1. 把 `SumSquares` 的参数改成 0，确认它返回 0，并且不会卡在接收上。
2. 去掉 `SumSquaresLocked` 的锁跑 `-race`，看竞争报告指到哪一行，然后把锁加回去。
3. 用 nil channel 关掉 `select` 的一支：收到停止信号后把数据 channel 变量设为 nil，确认循环还能在另一支上退出。

## 面试延伸

先说 goroutine 由运行时调度，栈会增长，但泄漏的 goroutine 仍然占内存。再说同步：`go` 语句同步启动之前的写；退出不同步，所以结果要用 channel、`Wait` 或锁交出来。`WaitGroup` 的 `Add` 在 `Wait` 之前，`Go` 的回调不能 panic。共享的 `sum +=` 是数据竞争，`-race` 只报告跑到的路径。

## 问答题

### 问：`SumSquares(4)` 为什么不用 `close`？

接收次数写死为 4。每个 goroutine 发送一次，主 goroutine 接收四次，双方都知道个数。参数是 0 时一次也不接收，直接返回 0。个数要由发送方决定、接收方事先不知道时，才由发送方关闭，接收方用 `range`。

### 问：平方和 30 是怎么来的？

1 到 4 的平方是 1、4、9、16，加起来是 30。Go 1.22 起循环变量每次迭代一份，闭包里的 `i` 不会都变成 4。

### 问：无缓冲 channel 谁先到谁等，这对内存模型意味着什么？

发送完成时，接收方已经拿走值。接收 happens before 对应的发送完成。所以接收方在收到值之后做的事，能看见发送方在发送之前做的写。退出 goroutine 本身没有这条保证。

### 问：两个 `select` case 都就绪，能断言走第一支吗？

不能。规范要求均匀的伪随机。`First` 的测试每次只让一支就绪。nil channel 的 case 不会被选中，可以用来关掉一支。

### 问：`WaitGroup.Go` panic 之后 `Wait` 会返回吗？

源码先 `Add(1)`，函数正常返回才 `Done`。panic 时把 panic 重新抛出，并且故意不 `Done`，避免 `Wait` 先返回、进程在 panic 完成前退出。任务自己要接 panic 并正常返回。

### 问：为什么不能在子 goroutine 里 `Add`？

主 goroutine 可能已经看到计数为 0 并从 `Wait` 返回。`Add` 要发生在启动之前。计数减到 0 以下会 panic。

### 问：`sum +=` 不加锁会怎样？

两个 goroutine 同时读改写同一个变量，是数据竞争。有数据竞争就没有顺序一致性。`go test -race` 只报告这次跑到的路径。能用 channel 交回结果时就不必共享 `sum`，`SumSquares` 是这种写法。

### 问：`main` 返回时后台任务的 defer 还会跑吗？

不会。进程退出，其它 goroutine 被停掉。要等的任务在 `main` 里 `Wait` 或接收完再返回。
