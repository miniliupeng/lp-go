# B2 context 与 slog

`context.Context` 携带截止时间、取消信号和少量请求范围的值。取消它不会把 goroutine 杀掉。函数要自己看 `ctx.Err()`，或者把 `ctx` 传给 `net/http`、`database/sql` 这类会监听它的 API。示例在 [examples/b2ctx](../../../examples/b2ctx/run.go)。

## 这一章你要会什么

会创建带取消原因和超时的 context，说清 `Err` 和 `Cause` 的差别，知道 context 里该放什么，会用 `slog` 打结构化日志并且不在热路径上做无用的参数求值。

## 取消是协作的

`WithCancel` 返回一个子 context 和 `cancel`。调用 `cancel` 之后，这个子 context 以及从它派生出去的 context 都结束。父 context 结束时，子 context 也结束。

`cancel` 要被调用，否则派生出去的 context 和内部的计时器会留到父 context 结束。`go vet` 的 `lostcancel` 会报告函数返回前没有调用 `cancel` 的情况。常见写法是拿到之后立刻 `defer cancel()`。

超时用 `WithTimeout` 或 `WithDeadline`。到期后 `Err` 是 `context.DeadlineExceeded`。超时仍然只是把 context 标成结束，堵在自己 channel 上的 goroutine 不会因此被抢下来。循环里要写：

```go
select {
case <-ctx.Done():
    return context.Cause(ctx)
case result := <-data:
    use(result)
}
```

## Cause

`RunSteps` 每一步先看 `ctx.Err()`。已经结束时返回 `context.Cause(ctx)`：

- context 还没结束时，`Cause` 返回 nil。
- `WithCancelCause` 的 `cancel(err)` 之后，`Err()` 仍是 `context.Canceled`，`Cause` 返回你传入的 `err`。`cancel(nil)` 时原因就是 `Canceled`。Go 1.27.1 的取消函数把空原因替换成 `Canceled`。
- `WithTimeout` 到期后，`Err` 和 `Cause` 都是 `context.DeadlineExceeded`。
- 父 context 先取消时，子 context 的 `Cause` 沿用父的原因。已经取消之后再次 `cancel`，原因保持第一次的。

调用方如果只看 `ctx.Err()`，只能分出取消和超时。要把「用户点了停止」和「下游拒绝」分开，用 `Cause`。

不要写成 `select` 同时等 `ctx.Done()` 和 `default`。context 已经取消时两边都就绪，`select` 会随机选一个，取消可能被丢掉。先 `if err := ctx.Err(); err != nil`，再做别的选择。

## 值

`WithRequestID` 用私有的键类型 `requestIDKey` 把字符串放进 context。键的类型是未导出的，别的包造不出同一个键，也就不会互相覆盖。

用字符串当键，两个包会撞车。把数据库连接、可选的全部业务参数、大块日志字段放进 context，调用链会变成一本看不见参数的字典。context 里放请求号、跟踪号这种「中间件写、日志读」的短值。业务参数放在函数参数里。

## 测试里的假时钟

超时测试放在 `testing/synctest` 里。气泡内的 `time.Sleep` 和 `WithTimeout` 使用假时钟，测试不用真的等一秒。`synctest.Wait` 会等到气泡里的 goroutine 都停在可等待的阻塞上。堵在 `Mutex` 上不算这种可等待的阻塞，不要在持锁的 goroutine 还没放开时调用 `Wait`。

## slog

`log/slog` 的 JSON Handler 一行一个对象。`logger.With("request_id", id)` 之后，`Info("hello")` 的输出里有 `"request_id":"req-7"`。级别过滤发生在 Handler。调用 `Debug` 时，参数表达式仍会先求值，然后 Handler 才决定丢不丢。极热路径写成：

```go
if logger.Enabled(ctx, slog.LevelDebug) {
    logger.Debug("...", "payload", expensive())
}
```

不要把密钥、完整的身份证号、未脱敏的令牌放进日志。请求号可以，用户密码不行。`With` 上放的字段每一条日志都会带上，放错一个大字段会把日志体积放大。

测试里把 Handler 的输出写进 `bytes.Buffer`，再检查有没有某个键。不要靠默认 logger 打到标准错误然后去抓进程输出。

## 对比陷阱

| 写法 | 实际结果 |
| --- | --- |
| 取消 context 就认为 goroutine 已经停了 | goroutine 要自己观察 `Done` 或 `Err` |
| `select` 里同时放 `ctx.Done()` 和 `default` | 两边都就绪时可能选中 `default`，取消被丢掉 |
| `cancel(nil)` 时期待 `Cause` 是 nil | 原因是 `context.Canceled` |
| 用字符串做 `WithValue` 的键 | 别的包可以用同一个字符串覆盖 |
| 热路径无条件调用 `Debug` 并构造大参数 | 参数先求值，级别过滤省不下这份工作 |
| 在 `synctest` 里对持有 `Mutex` 的 goroutine 调用 `Wait` | `Wait` 等的不是这种阻塞 |

```bash
go test ./examples/b2ctx -count=1
```

## 练习

1. 在 `RunSteps` 的测试里再取消一次已经取消的 context，确认 `Cause` 仍是第一次的原因。
2. 去掉 `defer cancel()`，跑 `go vet ./examples/b2ctx`，看 `lostcancel` 报在哪，然后加回去。
3. 给 logger 加一个 Debug 调用，参数里放一个会改变计数器的函数。在 Info 级别下确认计数器仍然增加，再改成先看 `Enabled`。

## 面试延伸

取消是协作的，不会杀 goroutine。`Err` 区分取消和超时，`Cause` 在 `WithCancelCause` 里给出业务原因，`cancel(nil)` 的原因是 `Canceled`。context 的值用未导出键类型，只放请求范围的短标识。`slog` 的级别在 Handler 里过滤，参数求值在调用之前，热路径先 `Enabled`。

## 问答题

### 问：取消 context 之后 goroutine 停在哪？

停在它自己写了 `<-ctx.Done()` 或检查了 `ctx.Err()` 的地方，或者停在一个会观察 context 的标准库调用里。堵在自己的 channel 上、又不看 context 的循环不会停。

### 问：`Cause` 和 `Err` 在三种结束方式下各是什么？

还没结束时 `Cause` 是 nil。`WithCancelCause` 的 `cancel(err)` 之后，`Err` 是 `Canceled`，`Cause` 是 `err`。`cancel(nil)` 时原因是 `Canceled`。`WithTimeout` 到期后两者都是 `DeadlineExceeded`。再次取消不改第一次的原因。

### 问：为什么不能 `select` `Done` 和 `default`？

已经取消时两边都可能就绪，伪随机可能选中 `default`，这一轮就看不见取消。先 `if err := ctx.Err(); err != nil`。

### 问：context 里为什么用未导出的键类型？

别的包造不出同一个类型的键，就不会覆盖你的请求号。字符串键会撞车。不要把数据库连接和整份业务参数放进去。

### 问：`lostcancel` 在找什么？

`WithCancel` 或 `WithTimeout` 返回的 `cancel` 在函数返回前没有被调用。惯例是立刻 `defer cancel()`。不调用的话，派生 context 要等到父 context 结束才释放。

### 问：`synctest` 为什么不用真的等一秒？

气泡里的时钟是假的。`WithTimeout(t.Context(), time.Second)` 可以被测试拨快。`Wait` 等到气泡里的 goroutine 都停在可等待的阻塞上。堵在 `Mutex` 上不算，不要在持锁时 `Wait`。

### 问：Info 级别下 `Debug` 的参数还会求值吗？

会。级别过滤在 Handler。热路径先 `Enabled`，再构造大字段。`With("request_id", id)` 之后每条日志都带这个字段。不要把密码放进 `With`。

### 问：父 context 先取消，子 context 的 `Cause` 是谁的？

沿用父的原因。子 context 上再调用自己的 `cancel`，已经结束的 context 保持第一次的原因。
