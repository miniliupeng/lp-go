# C1 内存、逃逸与内存模型

## 逃逸

函数返回局部变量的地址时，这个变量不能只活在栈上。`Leak` 返回 `&n`，Go 1.27.1 的编译器在 `-m` 输出里写 `moved to heap`。更早的编译器常写 `escapes to heap`。测试两种措辞都接受，并且要求输出里有 `Leak`。`Stay` 只返回一个整数，参数不必逃逸。

```bash
go test ./examples/c1escape -count=1
```

逃逸是编译器的决定。不要背「取地址就一定上堆」：如果地址没有离开函数，编译器仍然可以把它留在栈上。

## 切片扩容

`runtime/slice.go` 的 `nextslicecap`：需要的新长度大于旧容量的两倍时，直接用新长度；旧容量小于 256 时翻倍；否则按大约 1.25 倍增长，公式是 `newcap += (newcap + 3*256) >> 2`。之后还会按大小类向上取整，所以你观察到的 `cap` 可以比这个函数的返回值更大。它不是语言规范规定的常数。

容量还够时，`append` 写进原来的底层数组。见 [A3](../地基/A3-类型.md) 的测试。

## 内存模型

Go 的内存模型是 DRF-SC：没有数据竞争的程序，行为按顺序一致性理解。下面几条来自语言的内存模型，用来判断「另一个 goroutine 能不能看见这次写入」：

- `go` 语句的执行 happens before 新 goroutine 开始。
- goroutine 退出本身不把写入同步给别人。
- channel 上的发送 happens before 对应的那次接收完成。
- 关闭 channel happens before 因为关闭而收到零值的那次接收完成。
- 无缓冲 channel 上，接收 happens before 对应的发送完成。
- 容量为 C 的 channel 上，第 k 次接收 happens before 第 k+C 次发送完成。因此带缓冲的 channel 可以当计数信号量：缓冲容量就是同时持有的名额。
- 第 n 次 `Unlock` happens before 第 m 次 `Lock` 返回，其中 n < m。失败的 `TryLock` 不建立同步。
- 原子操作：如果 B 观察到了 A 的结果，则 A happens before B。`sync/atomic` 的操作是顺序一致的。

32 位平台上自己对齐 64 位原子变量容易踩坑，用 `atomic.Int64`。

## 练习

给 `Leak` 加一个只在函数内部取地址、又不返回的变量，用 `-gcflags=-m` 看编译器怎么说。把结论写在测试注释里，不要把某一版的英文提示当成永远不变的字符串。
