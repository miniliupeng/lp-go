# C3 GC

默认垃圾回收器是并发的、精确的、非分代的、非整理的标记-清除。分配按大小分档，每个 P 有自己的缓存。这段话来自 Go 1.27.1 `runtime/mgc.go` 的文件头。分配器的 mcache 和大小类在 [内存与逃逸](C1-内存与逃逸.md)。

## 这一章你要会什么

能按清扫终止、标记、标记终止、清扫四步讲一轮 GC，能区分文件头概述和 `mbarrier.go` 里的写屏障规则，能说出 `SetMemoryLimit` 统计什么、不统计什么。

## 不是 Green Tea

它不是 Green Tea GC。Green Tea 要 `GOEXPERIMENT=greenteagc` 才打开。默认构建使用 `internal/goexperiment/exp_greenteagc_off.go`，其中 `GreenTeaGC` 为 false。面试被问到「1.27 是不是已经换成 Green Tea」时，回答默认关闭，正文讲的是默认的三色标记-清除。

三色是标记用的颜色：白色还没访问，灰色已经发现但没扫完它的指针，黑色扫完了。精确是指回收器知道哪些字是指针。非分代是指没有「年轻代单独收集」这一层。非整理是指它不把活对象挪到一起去压缩堆。对象的地址在一轮回收里保持不变，所以内部指针可以指向对象中间。

## 一轮收集

`mgc.go` 里的周期：

1. **清扫终止**：短暂 STW，把上一轮还没扫的 span 扫完。只有这轮开始得比预期早，才会有未扫 span。
2. **标记**：STW 打开写屏障和辅助标记，把根放进队列，然后恢复。根包括栈、全局变量，以及运行时数据结构里的堆指针。扫栈时会停住对应的 goroutine。灰色对象被扫成黑色。分布式终止发现没有灰对象之后进入标记终止。标记期间新分配的对象直接是黑色。
3. **标记终止**：再一次 STW，关掉 worker 和 assist，刷新 mcache。
4. **清扫**：关掉写屏障，恢复世界。清扫和用户代码并发。清扫开始之后新对象是白色。

用户代码大部分时间和标记、清扫并发。停顿在两段 STW，加上扫某个 goroutine 的栈时停住那一个 G。不要把 Go 的 GC 说成「全程没有停顿」。

辅助标记（assist）让分配得多的 goroutine 帮忙做一点标记，避免分配速度远远超过标记速度。这是实现。知道「分配越猛，自己越要帮忙标记」即可。

## 写屏障

文件头的概述写「写屏障涂掉被覆盖的指针和新指针」。精确规则在 `runtime/mbarrier.go`：总是涂被覆盖的旧指针（Yuasa 删除屏障）；只有当前栈还是灰色时，才涂新指针（Dijkstra 插入屏障）。栈扫完变黑之后，删除屏障负责旧指针。

为什么需要它：标记和用户代码并发。用户把指针从对象 A 挪到对象 B 时，如果两边都不再被扫到，这个指针指向的对象会丢。涂灰保证它还会被扫描。

混合写屏障是上述两条的组合，不是第三种跟源码无关的说法。面试先说「总是涂旧指针」，再说「栈还是灰的时候才涂新指针」。把文件头的概述当成精确规则，会和 `mbarrier.go` 对不上。

## GOGC 与内存上限

`GOGC` 未设置时是 100：新分配的数据达到上一轮存活数据的这个百分比，就再触发一轮。`debug.SetGCPercent(-1)` 关掉按比例触发，内存上限仍然有效。测试不调用它，避免把进程的 GC 关掉。调用过的程序要在退出前把原来的百分比设回去。

`debug.SetMemoryLimit` 是软上限，单位字节。运行时会提高回收频率，并更积极地把内存还给操作系统。它统计的是运行时映射和管理、尚未释放的内存，不包括 Go 二进制本身、C 代码分配的内存，也不包括不由运行时管理的 `syscall.Mmap`。文档给出的表达式是：

```text
runtime.MemStats.Sys - runtime.MemStats.HeapReleased
```

用 `runtime/metrics` 则是 `/memory/classes/total:bytes` 减去 `/memory/classes/heap/released:bytes`。传入负数只读回当前值，不修改。测试把上限设成 512 MiB，再用负数读回，结束时恢复原值。

软上限不是硬性的 `malloc` 失败线。活对象本身已经超过上限时，运行时无法把它们收掉，进程的内存仍然可以高于这个数。它用来在活对象允许的前提下，更早触发回收、更早把页还给操作系统。

`ReadMemStats` 会短暂 STW，不要用它做高频打点。指标用 `runtime/metrics`，读的时候不要同时改那块 `Value` 缓冲区。名字写错时 `Kind` 是 `KindBad`，这时调用 `Uint64()` 会 panic。见 [熔断、重试与可观测性](../工程/D4-熔断重试与可观测性.md)。

```bash
go test ./examples/c3gc -count=1
```

## 对比陷阱

| 说法 | 实际情况 |
| --- | --- |
| Go 1.27 默认已经是 Green Tea | 默认 `GreenTeaGC` 为 false |
| GC 全程无 STW | 清扫终止和标记终止会 STW |
| 写屏障总是同时涂旧指针和新指针 | 新指针只在当前栈仍是灰色时涂 |
| `SetMemoryLimit` 把进程的所有内存算进去 | 不包括二进制、C 内存、运行时不管的 mmap |
| 设了上限，内存就一定不会超过它 | 活对象超过上限时收不掉 |
| 用 `ReadMemStats` 做每秒上千次的监控 | 每次都会短暂 STW |
| 把 `SetGCPercent(-1)` 留在进程里 | 按比例的触发被关掉。上限还在，但要记得恢复 |

## 练习

1. 读 `debug.SetMemoryLimit` 的注释，写出它不计入上限的三类内存。
2. 用自己的话写下混合写屏障的两条，再打开 `mbarrier.go` 对一遍。
3. 说明标记期间新对象是黑色、清扫开始后新对象是白色。各用一句说出这样做是在防什么。

## 面试延伸

开场用文件头的四个形容词：并发、精确、非分代、非整理。主动说 Green Tea 要实验开关。然后四步：清扫终止 STW、并发标记、标记终止 STW、并发清扫。写屏障按 `mbarrier.go` 说，不按文件头的概述说。内存上限给公式，并列出三类不计入的内存，加上「负数只读」和「活对象可以超过软上限」。

## 问答题

### 问：四个形容词各是什么意思？

并发：标记和清扫的大部分时间和用户代码一起跑。精确：知道哪些字是指针。非分代：没有单独的年轻代收集。非整理：不把活对象挪到一起，地址在这一轮里保持不变。

### 问：Green Tea 怎么打开？

`GOEXPERIMENT=greenteagc`。默认构建的 `exp_greenteagc_off.go` 里 `GreenTeaGC` 为 false。被问「1.27 是不是已经默认换成 Green Tea」时，回答不是。

### 问：两段 STW 各做什么？

清扫终止把上一轮还没扫完的 span 扫完，只有这轮开始得早才有未扫 span。标记终止关掉 worker 和 assist，刷新 mcache。中间的标记和后面的清扫与用户代码并发。扫某个 G 的栈时会停住那一个 G。

### 问：新对象在标记期间和清扫开始后各是什么颜色？

标记期间直接是黑色，避免刚分配就被漏标。清扫开始、写屏障关掉之后，新对象是白色，留给下一轮。

### 问：写屏障到底涂什么？

`mbarrier.go`：总是涂被覆盖的旧指针；只有当前栈还是灰色时才涂新指针。栈扫完变黑之后，靠删除屏障记住旧指针。文件头说「旧的和新的都涂」，那是概述，精确规则以 `mbarrier.go` 为准。

### 问：`GOGC=100` 是什么？

新分配达到上一轮存活数据的 100% 就再触发一轮。`SetGCPercent(-1)` 关掉按比例触发，内存上限仍有效。测试不调用它，避免把进程的比例触发关掉。

### 问：`SetMemoryLimit` 的公式和不计入的三类？

`MemStats.Sys - MemStats.HeapReleased`，或 `/memory/classes/total:bytes` 减去 `/memory/classes/heap/released:bytes`。不包括二进制、C 分配的内存、运行时不管的 `mmap`。负数只读。活对象已经超过上限时收不掉，所以它是软上限。测试把上限设成 512 MiB 再读回，结束时恢复。

### 问：为什么不用 `ReadMemStats` 做监控？

它会短暂 STW。高频打点用 `runtime/metrics`。名字写错时 `Kind` 是 `KindBad`，这时 `Uint64()` 会 panic。

### 问：assist 是什么？

分配得多的 goroutine 帮忙做一点标记，避免分配远远超过标记。知道「分配越猛，自己越要帮忙」即可，不必背函数名。
