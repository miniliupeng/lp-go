# C4 channel 与 select

语言规则以规范为准。实现对照 Go 1.27.1 的 `runtime/chan.go`。内存模型里 channel 建立的 happens-before 在 [内存与逃逸](C1-内存与逃逸.md)。入门用法在 [并发入门](../能写服务/B1-并发入门.md)。

## 这一章你要会什么

能按 `hchan` 的字段说明发送会进队列、进缓冲还是直接交给接收方，能把关闭、nil 和 `select` 的规则讲完整，能说明 Go 1.27 上计时器通道的容量为什么是 0。

## hchan

`hchan` 带有这些字段：`qcount`（缓冲里现有的元素个数）、`dataqsiz`（缓冲容量）、`buf`、`closed`、`sendx` 和 `recvx`（环形缓冲的下标）、`recvq` 和 `sendq`（堵住的接收方和发送方），以及一把锁。

源码写明两条不变量。发送等待队列和接收等待队列至少有一个为空。例外是同一个 goroutine 在一个 `select` 里同时等一个无缓冲 channel 的发送和接收。有缓冲时，缓冲区里有数据就不会有人堵在接收；还有空位就不会有人堵在发送。

发送的顺序，按 `chansend` 的代码：

1. channel 是 nil。阻塞发送会一直 park。非阻塞发送返回 false。
2. 非阻塞发送有一条不加锁的快路径：先看 `closed == 0`，再看缓冲和等待队列已经满。两个观察都成立时，直接返回 false。注释说明了为什么这两个字长的读可以代表「曾经有一个时刻，channel 还没关并且不能发送」。
3. 加锁之后如果已经关闭，解锁并 panic，信息是 `send on closed channel`。
4. 接收队列里有人在等，就把值直接交给这个接收方，不经过缓冲。
5. 缓冲还有空位，写入 `sendx`，下标按环前进，`qcount` 加 1。
6. 还是不能发：非阻塞就返回 false；阻塞就把自己放进 `sendq` 并 park。

接收是对称的。有人堵在发送，就直接取走对方的值。缓冲里有数据就从 `recvx` 取。关闭且已经取空，返回零值和 `ok == false`。

快路径只存在于非阻塞操作。普通的 `ch <- v` 是阻塞发送，不会走「满了就返回 false」那条。`select` 的 case 在试探时会用非阻塞路径。

## 关闭和 nil

[examples/c4chan](../../../examples/c4chan/chan_test.go) 测了这些规则：

| 操作 | 结果 |
| --- | --- |
| 关闭前缓冲里还有值 | 先取到那个值，`ok` 为 true |
| 已关闭并且取空 | 零值，`ok` 为 false |
| 向已关闭的 channel 发送 | panic |
| `close` 已关闭的 channel，或 `close(nil)` | panic |
| 对 nil channel 发送或接收 | 永远阻塞 |
| `select` 里的 nil channel | 不会被选中 |

只由发送方，或唯一负责关闭的那一方，关闭数据 channel。接收方关闭之后，发送方再发送会 panic。多个发送方时，不要让其中某一个随手 `close`。用一个专门的 `done` channel，或者由产生数据的那个循环在退出前关闭。

`for v := range ch` 一直取到关闭之后的零值。没有人关闭时，这个循环不结束。

## select

`select` 有多个 case 可以立刻进行时，实现用均匀的伪随机选一个。不要依赖书写顺序。一个 case 都没有时，`select {}` 永远阻塞。只有 `default` 时，`default` 在其它 case 都不能立刻进行时执行。

nil channel 的 case 被当成不存在。把已经不需要的那一支赋成 nil，循环里的 `select` 就只剩剩下的分支。这比再套一层布尔值少一个状态。

`select` 同时看 `ctx.Done()` 和 `default` 时，context 已经取消的情况下两边都可能就绪，取消会被 `default` 吃掉。先查 `ctx.Err()`。见 [上下文与日志](../能写服务/B2-上下文与日志.md)。

## 计时器

Go 1.23 起，计时器通道是同步的。Go 1.27 删除了 `asynctimerchan` 这个 GODEBUG。在本仓库的 Go 1.27.1 上，`cap(time.NewTimer(d).C)` 和 `Ticker.C` 的容量都是 0。测试锁住了这一点。

`Stop` 用来提前取消。`Reset` 在 Go 1.23 之后不会再把过期的时间留在通道里让你下一次误读。不再被引用的 Timer 和 Ticker 可以被 GC 回收。把 `time.After` 放进高频循环仍然会每次分配一个计时器，复用一个 `Timer` 并在用完后 `Reset`。

`time.After` 的通道在超时前一直堵着。函数已经返回、计时器还没到期时，这次分配要等到期才回收。请求路径上用 `context.WithTimeout`，让取消和超时走同一个 context。

## 泄漏

堵在一个再也等不到对方的 channel 上，就是 goroutine 泄漏。它不占着 P 干活，栈还在。Go 1.27 的 `goroutineleak` profile 能发现「堵在同步原语上，而且从任何可运行的 G 都到不了这个原语」的那一类。通过全局变量还能摸到的阻塞，它发现不了。见 [接口、反射与剖析](C6-接口反射与剖析.md)。

## 对比陷阱

| 说法 | 实际情况 |
| --- | --- |
| 有接收方在等时，值仍先入缓冲 | `chansend` 直接交给接收方 |
| 关闭之后接收立刻得到零值 | 缓冲里的值先被取完，`ok` 仍为 true |
| 接收方可以随手关闭数据 channel | 发送方再发送会 panic |
| `select` 按书写顺序优先 | 多个就绪 case 是伪随机 |
| Go 1.27 上 `Timer.C` 还是缓冲 1 的异步通道 | 本工具链上容量是 0，测试锁住了 |
| 循环里用 `time.After` 没有成本 | 每次调用都分配，到期前回收不了 |

## 练习

1. 写一个 `select`：数据 channel 和 `ctx.Done()`。先看 `ctx.Err()` 再进循环。
2. 缓冲里先放一个值再 `close`，连续接收两次，确认第一次 `ok` 为 true，第二次为 false。现有测试已经覆盖这条，读一遍并画出 `qcount`。
3. 非阻塞发送在 channel 为 nil 时返回 false。写一条 `select` 带 `default` 来观察它，不要用会永远堵住的发送。

## 面试延伸

先画 `hchan`：计数、容量、环、两个等待队列、关闭标志、锁。再讲发送的三条归宿：直接交给等待的接收方、写入缓冲、把自己放进 `sendq`。关闭题把「先取完缓冲」和「再发送会 panic」放在一起。`select` 题说伪随机和 nil case。计时器题说 1.27 上容量是 0，`Stop` / `Reset` 不再交出过期值，高频路径不要用 `time.After`。

## 问答题

### 问：`hchan` 上要说出哪些字段？

`qcount`、`dataqsiz`、`buf`、`closed`、`sendx`、`recvx`、`recvq`、`sendq` 和锁。有缓冲时，缓冲里有数据就不会有人堵在接收；还有空位就不会有人堵在发送。两个等待队列至少有一个为空，例外是同一个 goroutine 在一个 `select` 里同时等无缓冲 channel 的发送和接收。

### 问：有人堵在接收时，值会先入缓冲吗？

不会。`chansend` 加锁后如果 `recvq` 里有人，直接把值交给对方。没人等、缓冲还有空位，才写入 `sendx` 并前进下标。都满了，阻塞发送把自己放进 `sendq`。

### 问：非阻塞发送的快路径在做什么？

不加锁先看 `closed == 0` 并且已经满。两个字长的读如果都成立，返回 false。注释说明这两个观察可以代表曾经有一个时刻：还没关，并且不能发送。普通的 `ch <- v` 是阻塞发送，不走「满了就返回」这条。

### 问：关闭之后第一次接收一定是零值吗？

不一定。缓冲里的值先取完，`ok` 仍为 true。取空之后才是零值和 `ok == false`。再发送会 panic，信息是 `send on closed channel`。`close` 已关闭的 channel 或 `close(nil)` 也会 panic。

### 问：谁来关闭？

发送方，或唯一负责关闭的那一方。多个发送方不要各自 `close`。接收方关掉之后，发送方再发送会 panic。个数已知时可以不关闭，双方按次数收发，见 [并发入门](../能写服务/B1-并发入门.md)。

### 问：nil channel 在 `select` 里有什么用？

那个 case 不会被选中。把已经结束的一支赋成 nil，循环就只剩剩下的分支。对 nil channel 做普通发送或接收会永远阻塞。

### 问：Go 1.27 上 `Timer.C` 的容量？

测试锁住是 0。`Ticker.C` 也是 0。Go 1.23 起通道是同步的，1.27 删除了 `asynctimerchan`。`Stop` 和 `Reset` 不会再把过期值留在通道里。不再被引用的计时器可以被 GC 回收。`time.After` 放进循环会每次分配。

### 问：`goroutineleak` 能发现堵在 channel 上的所有泄漏吗？

不能。它找的是堵在同步原语上、并且从任何可运行的 G 都到不了这个原语的那一类。全局变量还能摸到的阻塞不在这个定义里。见 [接口、反射与剖析](C6-接口反射与剖析.md)。
