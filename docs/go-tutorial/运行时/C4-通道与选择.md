# C4 channel 与 select

语言规则以规范为准。`runtime/chan.go` 里的 `hchan` 带有 `qcount`、`dataqsiz`、`buf`、`closed`、`sendx`、`recvx`、`recvq`、`sendq` 和一把锁。源码写明：发送等待队列和接收等待队列至少有一个为空，例外是同一个 goroutine 在一个 `select` 里同时等一个无缓冲 channel 的发送和接收。有缓冲时，缓冲区里有数据就不会有人堵在接收；还有空位就不会有人堵在发送。

## 关闭

[examples/c4chan](../../../examples/c4chan/chan_test.go) 测了这些规则：

| 操作 | 结果 |
| --- | --- |
| 关闭前缓冲里还有值 | 先取到那个值，`ok` 为 true |
| 已关闭并且取空 | 零值，`ok` 为 false |
| 向已关闭的 channel 发送 | panic |
| `close` 已关闭的 channel，或 `close(nil)` | panic |
| 对 nil channel 发送或接收 | 永远阻塞 |
| `select` 里的 nil channel | 不会被选中 |

只由发送方，或唯一负责关闭的那一方，关闭数据 channel。接收方关闭之后，发送方再发送会 panic。

`select` 有多个 case 可以立刻进行时，实现用均匀的伪随机选一个。不要依赖书写顺序。

## 计时器

Go 1.23 起，计时器通道是同步的。Go 1.27 删除了 `asynctimerchan` 这个 GODEBUG。在本仓库的 Go 1.27.1 上，`cap(time.NewTimer(d).C)` 和 `Ticker.C` 的容量都是 0。测试锁住了这一点。`Stop` 用来提前取消。不再被引用的 Timer 和 Ticker 可以被 GC 回收。把 `time.After` 放进高频循环仍然会每次分配，复用一个 `Timer` 并 `Reset`。

堵在一个再也等不到对方的 channel 上，就是 goroutine 泄漏。Go 1.27 的 `goroutineleak` 能发现「堵在同步原语上，而且从任何可运行的 G 都到不了这个原语」的那一类。见 [C6](C6-接口反射与剖析.md)。

```bash
go test ./examples/c4chan -count=1
```
