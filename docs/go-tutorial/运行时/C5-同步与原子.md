# C5 sync 与 atomic

示例在 [examples/c5sync](../../../examples/c5sync/sync_test.go)。锁建立的 happens-before 在 [内存与逃逸](C1-内存与逃逸.md)。`WaitGroup` 的 `Add` 和 `Go` 在 [并发入门](../能写服务/B1-并发入门.md)。

## 这一章你要会什么

能说明 Mutex 的正常模式和饥饿模式，知道它不可重入、不能复制，能说出 `Once`、`Pool`、`sync.Map` 各自适合什么，能判断一段逻辑用原子够不够。

## Mutex

`Mutex` 不是可重入的。同一个 goroutine 再 `Lock` 一次会把自己堵死，因为锁的持有者信息不会识别「是我自己」。需要重入时把临界区拆开，或者用别的结构，不要在持锁时调用一个可能再次获取同一把锁的函数。

锁不能复制。复制会把等待队列切走，两个副本各有各的状态。结构体里嵌了 `Mutex` 之后，这个结构体也不要按值传递。`go vet` 的 `copylocks` 会报告按值传递。

`RWMutex` 允许多个读者或一个写者。写锁和读锁不能同时持有。在读锁里再申请写锁会死锁：写锁要等读者释放，读者要等写锁，读者就是自己。读远多于写、读的临界区不短时才考虑它。读者很少时，一把 `Mutex` 更简单。

Go 1.27.1 的 `internal/sync/mutex.go` 有两种模式。正常模式新来的 goroutine 会和等待者抢，这样刚释放锁的那一方如果立刻再来，缓存还热，吞吐更好，代价是队头可能连续抢不到。等待时间超过 `starvationThresholdNs`（`1e6` 纳秒，也就是 1 毫秒）后进入饥饿模式，锁直接交给队头。队头是新来的、等待时间没超过阈值时，可以回到正常模式。这是实现，用来说明「Mutex 不保证完全公平，但会避免一直抢不到」。不要把 1 毫秒背成语言规范。

`Unlock` 没人 `Lock` 时会 panic。把 `Unlock` 放在 `defer` 里，函数中途 `return` 也不会忘。`defer` 的成本在这把锁的临界区很短、调用极频繁时再考虑，先保证正确。

## Once

`sync.Once` 保证函数只执行一次。测试里 4 次 `Do` 只有 1 次把计数加上。并发的 `Do` 会等第一次执行完。

`Do` 里的函数如果 panic，这一次 `Once` 会认为已经做过了，后来的 `Do` 不会再试。初始化失败却不应该永久失败时，不要用 `Once` 包住会 panic 的代码。用 `Mutex` 加上显式的错误，让下一次调用可以重试。

`Once` 不能复制，原因和 `Mutex` 一样。

## Pool 和 victim

`sync.Pool` 用来复用临时对象，降低分配压力。`Get` 拿不到时调用 `New`。用完 `Put` 回去。测试先 `Get` 再 `Put` 再 `Get`，`New` 只调用一次。

池里的对象可以在任何时候被清掉，不通知你。GC 发生时，`pool.go` 会丢掉上一轮的 victim 缓存，再把当前的本地缓存挪去当 victim。于是一个对象大约能再活过一轮收集，下一轮就没了。这是实现，用来说明「Pool 会在不用时缩回去」。它不是缓存：不能假设 `Put` 进去的还能 `Get` 到，也不能在里面放连接这种必须被关闭的资源。

`Get` 到的对象要当成脏的，使用前自己重置字段。`Put` 一个还带着上一次请求数据的 `bytes.Buffer` 而不 `Reset`，下一个用户会读到上一个人的字节。

短命对象自己的空闲链表不适合用 `Pool`。`Pool` 的文档写的是：在多个客户端之间摊掉分配成本，例如 `fmt` 的临时缓冲。

## sync.Map

`sync.Map` 的文档说，大多数代码应该用普通 map 加锁。它适合两类：键写一次之后基本只读；多个 goroutine 各自碰各自的键，很少重叠。测试只演示 `Store` / `Load`。

它没有 `Len`，遍历用 `Range`。它不做 TTL，也不提供「没有这个键就去数据库加载」这种原子操作。缓存的击穿和过期在 [缓存与限流](../工程/D3-缓存与限流.md)，用的是带锁的 map，不是 `sync.Map`。

普通 map 的并发写会 panic。加锁的临界区里不要做 RPC。锁只包住 map 的读写，网络放在锁外面，结果再用一次短的锁写回去。

## 原子

`atomic.Int64` 的 `Add` 和 `Load` 是顺序一致的。一个计数器、一个标志位，用它可以。

下面这种复合动作用原子不够：先 `Load` 一个状态，根据状态去改另一块内存，再 `Store` 新状态。两步之间别的 goroutine 可以插进来。这种逻辑用 `Mutex`。

`CompareAndSwap` 适合「只在还是旧值时改成新值」的单字。CAS 循环在竞争激烈时会空转，而且仍然只保护这一个字。

64 位原子在 32 位平台上要对齐。用 `atomic.Int64` 和 `atomic.Uint64`，不要自己拿 `uint64` 的地址去做 `atomic.AddUint64`，除非你能保证对齐。

`atomic.Value` 可以原子地替换一个接口值，适合「整体换上一份只读配置」。读的人拿到的是某一代完整配置，不会看到写了一半的结构体。配置字段要一个一个改时，它不合适。

## 对比陷阱

| 说法 | 实际情况 |
| --- | --- |
| Mutex 公平，先来先得 | 正常模式会抢。超过实现里的 1 毫秒才进入饥饿。1 毫秒不是规范 |
| 同一个 goroutine 可以再次 Lock 同一把 Mutex | 不可重入，会把自己堵死 |
| `Once` 的函数 panic 后下次会重试 | 已经算做过 |
| `Pool` 可以当连接池或 TTL 缓存 | 对象会被清掉，`Get` 不保证拿回你 `Put` 的那个 |
| `sync.Map` 在所有场景都更快 | 文档建议大多数代码用 map 加锁 |
| 两个原子操作合在一起就是临界区 | 中间可以交错 |

1. 把 `TestMutexOnceAtomic` 里的锁去掉，用 `go test -race` 看竞争报告，然后把锁加回去。
2. 从 `Pool` 里 `Get` 一个 `*bytes.Buffer`，写入后再 `Put`。下一次 `Get` 之前先想它里面可能还有旧字节，写上 `Reset`。
3. 用 `atomic.Value` 存一份只读的小结构体，一个 goroutine `Store` 新值，另一个 `Load` 后只读。不要在 `Load` 到的指针上写字段。

## 面试延伸

Mutex：不可重入、不可复制、正常模式会抢、饥饿阈值是实现里的 1 毫秒。`Once`：成功只跑一次，panic 也算完成。`Pool`：临时对象，GC 时主缓存降为 victim，再一轮丢掉，不是缓存。`sync.Map`：两种适合的访问模式，其余用锁。原子：单字可以，复合动作用锁，配置整份替换可以用 `atomic.Value`。

## 问答题

### 问：同一个 goroutine 能再次 `Lock` 吗？

不能。Mutex 不记录「持有者是不是我」。再次 `Lock` 会把自己堵死。不要在持锁时调用一个可能再拿同一把锁的函数。

### 问：为什么不能复制锁？

复制把等待队列切成两份。含有 `Mutex` 的结构体不要按值传递。`go vet` 的 `copylocks` 会报告。`Once` 同样不能复制。

### 问：饥饿模式的 1 毫秒从哪来？

`internal/sync/mutex.go` 的 `starvationThresholdNs` 是 `1e6` 纳秒。正常模式新来的 goroutine 会和等待者抢。等待超过这个阈值后，锁交给队头。这是实现，不是语言规范。

### 问：读锁里能升级成写锁吗？

不能。写锁要等读者释放，读者要等写锁，读者就是自己。要写就先放开读锁，或者一开始就用 `Mutex`。读者非常多、临界区不短时才考虑 `RWMutex`。

### 问：`Once` 里的函数 panic 了，下次会重试吗？

不会。panic 也算这一次已经做过。初始化失败还想重试时，用 `Mutex` 和显式的错误，不要用 `Once`。

### 问：`Pool` 的 victim 是什么？

GC 时丢掉上一轮的 victim，再把当前的本地缓存挪去当 victim。对象大约再活过一轮收集。`Get` 不保证拿回你 `Put` 的那个。拿出来要当成脏的，`bytes.Buffer` 先 `Reset`。不要把必须 `Close` 的连接放进去。

### 问：`sync.Map` 的两种场景？

键写一次之后基本只读；多个 goroutine 各自碰各自的键。其余用 map 加锁。它没有 TTL，也没有「没有就去加载」的原子操作。临界区里不要做 RPC。

### 问：两个 `atomic.Int64` 能组成临界区吗？

不能。每个操作自己是顺序一致的，两步之间别人可以插进来。复合动作用 `Mutex`。整份只读配置可以用 `atomic.Value` 替换，读的人拿到的是某一代完整值，不要在 `Load` 到的结构上写字段。
