# C5 sync 与 atomic

示例在 [examples/c5sync](../../../examples/c5sync/sync_test.go)。

## Mutex

`Mutex` 不是可重入的。同一个 goroutine 再 `Lock` 一次会把自己堵死。锁不能复制：复制会把等待队列切走。`go vet` 的 `copylocks` 会报告按值传递。

Go 1.27.1 的 `internal/sync/mutex.go` 有两种模式。正常模式新来的 goroutine 会和等待者抢。等待时间超过 `starvationThresholdNs`（`1e6` 纳秒，也就是 1 毫秒）后进入饥饿模式，锁直接交给队头。这是实现，用来说明「Mutex 不保证完全公平，但会避免一直抢不到」。不要把 1 毫秒背成语言规范。

`RWMutex` 适合读远多于写。写锁不能和读锁同时持有。在读锁里升级成写锁会死锁。

## Once、Pool、Map

`sync.Once` 保证函数只执行一次，测试里 4 次 `Do` 只有 1 次把计数加上。`Do` 里的函数如果 panic，这一次 `Once` 会认为已经做过了，后来的 `Do` 不会再试。

`sync.Pool` 用来复用临时对象，降低分配。测试先 `Get` 再 `Put` 再 `Get`，`New` 只调用一次。GC 可以清掉池里的对象，所以它不是缓存。见 [D3](../工程/D3-缓存与限流.md)。

`sync.Map` 的文档说，大多数代码应该用普通 map 加锁。它适合写一次、读很多次，或者每个键几乎只被一个 goroutine 碰到。测试只演示 `Store` / `Load`。不要把它当成 TTL 缓存。

## 原子

`atomic.Int64` 的 `Add` 和 `Load` 是顺序一致的，见 [C1](C1-内存与逃逸.md)。用它保护一个计数器可以；用它保护「先看 map 再改另一块内存」这种复合动作则不够，那种情况用 `Mutex`，让锁把几步包在一起。

`WaitGroup` 的用法在 [B1](../能写服务/B1-并发入门.md)。`Go` 的文档要求回调不要 panic。

```bash
go test ./examples/c5sync -count=1
```
